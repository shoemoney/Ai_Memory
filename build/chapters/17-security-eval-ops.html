Threats

Memory carries text into later prompts, making every writer a potential attacker.

OWASP calls this ASI06, Memory and Context Poisoning.1 An OWASP co-lead treats memory, hooks (automatic harness-event scripts) and configuration as trusted environment; edits give attackers standing access.2

Terms new in this chapter

Memory poisoning
False or hostile text saved for later sessions.

Where untrusted text enters and where it comes back

Rule: retrieved memory is data, never instructions

Quote retrieved text with application-controlled source/trust labels (provenance and review state). Block edits to hooks, configuration, system prompts and tool allowlists. Review tool/web content before writes; test every release, including benign writes against reviewers (Release gate).

Published attacks and reduced labs

MINJA plants memories through normal queries and outputs, without store write access.3 AgentPoison optimizes a query trigger to retrieve poisoned memory or knowledge-base entries.4

Published figures were not reproduced. Reduced poisoning labs follow; inversion is discussed below.

Local MINJA and AgentPoison labs used Qwen2.5-3B-Instruct Q4_K_M, 100 trials per arm (companion repository, benchmarks/security; revision pinned in manifest). Defenses ran together: the same model reviewing writes, a recall filter accepting only records the application labels trusted/reviewed, and retrieved text quoted with source labels. Combined defenses cannot reveal which blocked attacks or reduced accuracy. Separate costs were measured: harmless-write rejection and ordinary-answer accuracy on existing records. MINJA answer accuracy fell from 100/100 to 71/100 with defenses. AgentPoison accuracy was 91/100 clean, 90/100 poisoned and 77/100 under attack with defenses. Poisoning cost one percentage point (95% interval 0.0 to 3.0 percentage points), too imprecise to confirm or refute the paper's less-than-1% claim. High recall can coexist with poison; include poisoning regression probes.

A single interaction can persist

InjecMEM crafts a message the agent stores and retrieves for a targeted topic, without store access. Released write/retrieval classifiers offer no guarantees. Test targeted topics and unrelated benign queries.7

A reduced lab directly inserted the released 7B-family-optimized payload, skipping extraction, compaction, fresh optimization and full MemoryOS tiered memory management. Payload retrieval and attack success were each 0/100; conditional success is undefined without retrievals. This cannot assess the paper's attack.

Persistent injections have reached ChatGPT memory through untrusted content and Claude Code memory and hooks through a cloned repository; both were fixed.89

Poisoned learned skills

SkillJack disguises malicious experiences as durable skills surviving source deletion.10 Controls to try:

  • Link skills to source experiences.
  • Require review plus benign and hostile activation tests before promotion.
  • Revoke skills with their sources; test deletion across layers.

Detecting direct store tampering

A September 2026 preprint tested store edits in LangGraph's SQLite checkpointer 3.1.1, Letta 0.16.8 and Mem0 2.0.20. All 15 edits reportedly passed silently, including forged insertions. The attacker has storage access; results cover only these pinned versions.11

Locally, the five edit classes, forged insertions included, were accepted in all 1,500 trials on those three releases (15 edit and release cells, 100 repeats each). Per-store keyed hash chains, keys/latest hashes held externally, caught all 1,500 storage-only attacks. Key management, concurrent writers and performance were not tested. Controls to try:

  • An append-only audit log whose entries hash the previous entry.
  • Signed writes, with signing keys kept outside the store.
  • An independently retained signed log head detecting truncation.
  • Check chains/signatures on every read/restore; audit access/failures. On failure, quarantine, stop serving and alert; recover from an independently verified log head. Never re-sign suspect state.

OWASP recommends tamper detection, read-only log copies and monitored log access.12

Cross-user leakage

Shared vector databases can leak memories across users. OWASP's LLM08 entry recommends permission-aware stores, logical partitioning, source validation and immutable retrieval logs.13 Use store-enforced row policies or credentials restricted to a tenant partition. With shared credentials spanning partitions, isolation depends on the trusted retrieval service.14 Bind namespaces to authenticated identity; probe cross-user IDs in vector/keyword search, graph expansion, summaries, caches and restored indexes.

Gotcha: checkpoint stores have had real CVEs

Check installed langgraph-checkpoint and langgraph-checkpoint-sqlite. The SQLite checkpointer saves per-step thread state; langgraph-checkpoint-sqlite 3.0.1 fixes CVE-2025-67644, a SQL injection in its metadata filter.15 CVE-2025-64439, a deserialization flaw, is fixed in langgraph-checkpoint 3.0.0. Check Point reports the two chain to reach code execution.16 Never let end users control checkpoint history filters, and delete checkpoints with the thread as personal data.

Inversion, secrets and personal data

Embeddings can reveal source text, so a vector index is not anonymized.6 A reduced local attack on 4-bit GTR-base and Vec2Text models (five correction rounds, where the paper uses 50 plus a wider search) exactly recovered 0/100 synthetic 32-token texts, though the output shared most of its words with the original (word overlap 0.724); it does not match the published 92%. Exclude secrets at write time; reference them by ID. The lab embedded bare opaque references and vaulted text separately, removing semantic matching for those records; retrieval utility was unmeasured.

Privacy and deletion

Delete across the source records and everything derived from them. Engines differ: PostgreSQL retains dead rows until vacuum makes space reusable, usually without returning it to the operating system.17 Check logical invisibility, disk reclamation and backup erasure separately.

Crypto-shredding destroys encryption keys to make data unreadable. Every copy must use that key, without recoverable key copies. Volume encryption cannot selectively erase one tenant while preserving others. Inventory plaintext exports/logs and derived data surviving key destruction.

Inventory source/derived copies, erasure/retention deadlines and completion records. Scope retention exceptions, restrict access, set expiry and test absence across layers. Agree requirements with your privacy team; this is no legal-compliance determination.18

A private regression set

Test scrubbed interactions on every change.

  • Contents: labeled questions on expected facts, supporting IDs, updates and abstentions, plus poisoning cases, cross-tenant probes and correction and deletion races.
  • Versioning: store the model, extractor, chunking and judge settings with the dataset.
  • Metrics: recall@k (fraction of expected supporting IDs in the top k, averaged over questions with at least one; score abstentions separately), answer accuracy, stale answers, conflicting facts, durable write precision (accepted writes still correct once built) and invalid outputs. Report poisoning and tenant leaks separately, check judge decisions by hand and keep every failure.

Periodically sample records per tenant; label accurate, stale or junk, and delete or re-extract stale/junk items. One user judged 9,911 of 10,134 entries junk; that self-report was not checked here and is not an expected rate.29

Cost, consistent writes and operations

Calls and tokens per write and per read

Flat files need no embeddings. Vector retrieval embeds writes and queries (Chapter 03). Extraction adds fact/update decisions; graphs add entity resolution/invalidation.3031 Count retries and added prompt tokens.

Mem0 reports 91% lower p95 latency and over 90% fewer tokens than full context for one workload.26 Wolff and Bennati report plain RAG with comparable accuracy at 8.4 times lower total cost than Mem0; not reproduced here.27 On 123 matched LoCoMo questions across four histories, Mem0 used 97.8% fewer read-path input and output tokens combined than full context but only 27.2% fewer on the same basis including ingestion. Its p95 answer latency was higher (11.41 versus 5.82 seconds). Possible explanations include short histories, local 4-bit inference and uncontrolled prefix-cache reuse speeding full context. Measure locally. Counting LLM input/output tokens (extraction included, embedding omitted), Mem0 cost 11.6 to 20.8 times as much as dense RAG across the four histories.

Break-even between full context and memory

One study reports Mem0-style memory cheaper after about ten turns at 100,000 cached tokens; long context was more accurate on LongMemEval and LoCoMo.32 At $0.15, $0.075 and $0.60 per million uncached input, cached input and output tokens (GPT-4o mini list rates checked 22 November 2026; full-context prefix cached after the first question), one 34-question history cost $0.1010 to ingest, saving $0.00435 on question one (uncached input) and $0.002125 thereafter. Projected payback is 1 + ceil((0.10095 − 0.00435) / 0.002125) = 47 questions. Pooled payback projects 49 questions for Mem0 and 51 for Graphiti, beyond the observed 24 to 34. Their 95% bootstrap intervals, resampling four whole histories, were 48 to 51 and 45 to 63, respectively; Mem0 per-history estimates ranged from 47 to 52. These extrapolations assume read-only questions after ingestion. Per-turn writes delay break-even. Ignoring price and caching, Mem0 uses 27.2% fewer tokens at the observed mean of about 31 questions per history; cheaper cached input delays dollar payback. Uncosted storage, embedding and maintenance must also be repaid by repeated reads. If full context cannot fit or suffice, compare the cheapest capable baseline.

A consistency protocol for asynchronous writes

Protocol terms

Outbox
Work committed atomically with source changes; a worker builds the projection later.
Projection
The searchable copy built from a source record.
Tombstone
A deletion record (Chapter 12) preventing resurrection during rebuilds.

The store commits saves/deletes before workers build projections. Figure 2 includes idempotent retries/dead letters. The worker checkpoint, separate from thread state, advances after every event through its sequence finishes or dead-letters. Gaps block advancement; restarted workers resume after it.33 This proposed protocol is not standardized.

  1. Accept. Authenticate the tenant; atomically commit the new source version and outbox entry. Store an HMAC of tenant, memory ID, operation and payload under each tenant-scoped event ID. Retries return the original receipt; changed payloads are rejected.
  2. Materialize. Publish only current source versions so slow jobs cannot overwrite newer data. Tag derived items with tenant, extractor revision and all contributing source IDs/versions. Hide items with deleted, superseded or unauthorized dependencies; rebuild from authorized sources before serving. Commit the projection update and its delivery row (in the delivery table) together if possible.
  3. Retry. Retry with bounded backoff/jitter; then flag a dead letter for an operator: terminal for checkpointing but unsuccessful, automatic delivery stopped. Record attempts/redacted errors, alert on queue age/dead letters, and retry the same event ID after repair.
  4. Checkpoint. Advance only past terminal events, including dead letters; never skip gaps.
  5. Delete. Commit a versioned tombstone, remove source text, hide stale reads immediately and delete derived items. Use a new memory ID for replacements to prevent stale-write resurrection.
  6. Rebuild. Rebuild from authorized sources and tombstones. Erasure-safe restores need a separately recoverable tombstone ledger covering every restorable snapshot. Current-state restores also replay committed updates to a verified position before serving. If later updates are lost, declare the recovery-point objective (maximum tolerable data loss). Probe a corrected, never-deleted record after restore.

Remote indexes retain text-free versioned tombstones until workers finish and retention expires. Write only newer versions before recording delivery locally; crash redelivery safely repeats writes. Without conditional writes, process one memory ID at a time and compare index against source. Retrieve candidate IDs, then hydrate/filter against current authorized sources before prompting. Version equality hides the entire record during lag, indefinitely on dead letters. For read-after-write, await materialization or read source. See also Chapter 13, Forked planning: draft locally, promote explicitly.

db.executescript('''
CREATE TABLE source(id TEXT PRIMARY KEY, v INT, gone INT, text TEXT);
CREATE TABLE outbox(seq INTEGER PRIMARY KEY AUTOINCREMENT, tenant TEXT, eid TEXT,
  mid TEXT, v INT, gone INT, request_hash TEXT, attempts INT DEFAULT 0,
  state TEXT DEFAULT 'pending', UNIQUE(tenant,eid));
CREATE TABLE projection(id TEXT PRIMARY KEY, v INT, gone INT, text TEXT);
CREATE TABLE delivery(tenant TEXT, eid TEXT, PRIMARY KEY(tenant,eid));
CREATE TABLE checkpoint(n INT);
INSERT INTO checkpoint VALUES(0);
''')

def key(tenant, mid):
    return json.dumps([tenant, mid], separators=(',', ':'))

def enqueue(eid, mid, text=None, tenant='demo'):
    operation = 'delete' if text is None else 'put'
    request = json.dumps([tenant, mid, operation, text],
                         ensure_ascii=False, separators=(',', ':'))
    digest = hmac.new(secret, request.encode('utf-8'), hashlib.sha256).hexdigest()
    mid = key(tenant, mid)
    with db:
        db.execute('BEGIN IMMEDIATE')
        prior = db.execute('''
          SELECT request_hash,seq,v FROM outbox WHERE tenant=? AND eid=?
        ''', (tenant, eid)).fetchone()
        if prior:
            if prior[0] != digest:
                raise ValueError('event ID reused with a different request')
            return prior[1:]  # original acceptance receipt, even after deletion
        row = db.execute('SELECT v,gone FROM source WHERE id=?',
                         (mid,)).fetchone()
        if row and row[1] and text is not None:
            raise ValueError('deleted ID; create a new memory ID')
        v = row[0] + 1 if row else 1
        gone = int(text is None)
        db.execute('INSERT OR REPLACE INTO source VALUES(?,?,?,?)',
                   (mid, v, gone, text))
        result = db.execute('''
          INSERT INTO outbox(tenant,eid,mid,v,gone,request_hash) VALUES(?,?,?,?,?,?)
        ''', (tenant, eid, mid, v, gone, digest))
        return (result.lastrowid, v)

def deliver(eid, fail=False, tenant='demo'):
    with db:
        db.execute('BEGIN IMMEDIATE')
        if db.execute('SELECT 1 FROM delivery WHERE tenant=? AND eid=?',
                      (tenant, eid)).fetchone():
            return
        seq, mid, v, gone, attempts = db.execute('''
          SELECT seq,mid,v,gone,attempts FROM outbox WHERE tenant=? AND eid=?
        ''', (tenant, eid)).fetchone()
        if fail:
            attempts += 1
            db.execute('UPDATE outbox SET attempts=?,state=? WHERE tenant=? AND eid=?',
                       (attempts, 'dead' if attempts >= 3 else 'pending', tenant, eid))
        else:
            current = db.execute('SELECT v,gone,text FROM source WHERE id=?',
                                 (mid,)).fetchone()
            if current[0] == v:
                db.execute('''
                  INSERT INTO projection VALUES(?,?,?,?)
                  ON CONFLICT(id) DO UPDATE SET
                    v=excluded.v,gone=excluded.gone,text=excluded.text
                  WHERE excluded.v > projection.v
                ''', (mid, v, gone, current[2]))
            db.execute('INSERT INTO delivery VALUES(?,?)', (tenant, eid))
            db.execute("UPDATE outbox SET state='done' WHERE tenant=? AND eid=?",
                       (tenant, eid))
        n = db.execute('SELECT n FROM checkpoint').fetchone()[0]
        while db.execute('''
          SELECT 1 FROM outbox WHERE seq=? AND state IN ('done','dead')
        ''', (n + 1,)).fetchone():
            n += 1
        db.execute('UPDATE checkpoint SET n=?', (n,))

def read(mid, tenant='demo'):
    mid = key(tenant, mid)
    return db.execute('''
      SELECT p.text FROM projection p JOIN source s ON s.id=p.id
      WHERE p.id=? AND s.gone=0 AND p.gone=0 AND p.v=s.v
    ''', (mid,)).fetchall()

Harden the lab network

Docker publishes to all host interfaces by default; in the book's database and model-server labs, bind ports to 127.0.0.1, or publish none and use a private network.36 Before LAN access, authenticate databases/model-server proxies; Ollama's API defaults to unauthenticated loopback access.37,38 Before Docker 28.0.0, localhost-published ports may be segment-reachable; upgrade or enforce firewall isolation.36

Operate the memory path

Log tenant, source version, retrieval score and opaque record-version ID under access/retention controls. Correlate text via tenant-scoped HMACs, external keys and defined retention; never log plaintext. Back up sources/tombstones; test restores in quarantine. For embedding migration, build a shadow index (serving no reads), pin model revision and dual-write via outbox. Record the last committed sequence. Switch after its worker checkpoint reaches that sequence without dead letters, tenant/deletion probes pass, and private-regression recall@k and accuracy match the live index. Dual-write deletes while rollback remains possible. Consolidation (merging/summarizing memories) needs live-write version/deletion checks against resurrection.39

Release gate

Check writes before launch and after model/prompt changes. Record release margins/budgets against current controls and workload requirements.

  • Test cross-tenant retrieval, poisoning, correction races, delete, replay, restore (including corrected, never-deleted records) and source/tombstone rebuilds; require latest authorized versions on reads.
  • Compare representative private tasks with no-memory/current-release controls; report completion, cost and latency. Add task-matched MemoryArena or DolphinBench comparisons. Fail on confirmed cross-tenant retrieval, action-changing poison, completion below the control by a preset margin, or cost/p95 latency over preset budgets.
  • Commit labeled harmless facts/corrections, await materialization, query in a fresh session; require a preset share correct. Report hostile-write acceptance and benign-write rejection as counts/denominators; fail above either preset budget or the answer-accuracy-loss budget.
  • Monitor queue age, retries, dead letters, stale-version skips and delete completion in every derived store.

Forward example. Chapter 22 applies these controls to a doctor's office: per-patient scoping, an append-only audit trail, tombstones that survive a restore.
