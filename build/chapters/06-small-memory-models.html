Small LLMs as memory models

A small chat model on your own machine reads conversations and writes down the facts worth keeping.

Maturity

Shipped

Setup effort

3 of 5

Running cost

2 of 5

Best for

Private memory that must stay on your hardware and runs in the background.

What it is

A small language model, the writer, records conversation facts in the store's format. Most have 1 to 9 billion parameters. Mixture-of-experts models select parameter groups (experts) per token: 30B-A3B runs about 3 billion parameters but stores all 30 billion.

The chat model writes notes; an embedding model encodes them for similarity search (Chapter 03). Memory usually needs both.1

Terms new in this chapter

Mem0 v3
The open-source memory algorithm in the pinned mem0ai==2.2.1 Python package; algorithm and package versions are numbered separately.2,37
Extraction
Turning conversation into separate facts or entities.
Constrained decoding
Restricting output tokens to a schema or grammar.
Thinking mode
Writing reasoning before the answer.
Weight quantization
Storing weights with fewer bits, such as 4, so the model needs less memory. The GGUF labels Q4_K_M and Q8_0 mean roughly 4-bit and 8-bit.
GGUF
A single-file model format used by llama.cpp and Ollama.

The glossary defines parameters, tokens and context window.

How it works

What each framework asks of the model

On saves and sometimes reads, writers extract facts, reconcile changes and duplicates, summarize or answer recall questions.

FrameworkOn writeOn read
Mem0 (v3 algorithm)Mem0 retrieves up to ten related memories, asks the model once for new facts, then removes exact duplicates by hash.2It retrieves candidates by embedding similarity; when enabled, BM25 lexical scores and named-entity matches only reorder them (Chapter 13, Gotchas). The README also lists time-aware ranking. It describes no model call on read.2,3
Hindsightretain pulls out facts, dates, entities and relationships with a model.4recall runs four searches in parallel and merges them. reflect asks the model for deeper synthesis.4
GraphitiEntity and edge extraction plus deduplication, all as structured JSON.5Search over the graph. The README does not describe model use on read.
Letta sleep-time agentsA second agent edits memory blocks while the main agent is idle.6Memory can be read at any time, because editing happens off to the side.6

These sources recommend no small model. Test your candidate writer on representative conversation turns with the framework's actual prompt and output format. Where permitted, retain access-controlled transcripts for failed extractions; delete them with the memories (Chapter 17).

Why reliable JSON matters

Graphiti "depends on structured (JSON) output".5 Constrain decoding to prevent missing fields and prose wrappers; validate identifiers against the store and check for truncation.

Constrained decoding blocks schema-breaking tokens. Ollama takes a schema in format.10 llama.cpp supports GBNF grammars11 and OpenAI-compatible response_format with type json_schema (step 3). Reject truncation, refusal and runtime errors, then validate fields; a schema cannot make facts true.

Tested With llama.cpp, constrained output and thinking off, Qwen3.5 4B returned valid JSON on 79 of 100 prompts with a narrow three-field schema. All 21 failures repeated to the output limit; doubling it rescued none. General-schema validity was 100 percent (Numbers); narrow-schema prompts are in benchmarks/extraction/v1/data/sample.json. Test your shipping schema. Use repetition penalty 1.1 only for this failure: it gave 100 of 100 but lost facts on the broader test (Numbers). Set repeat_penalty in the llama.cpp request body or Ollama options. Treat 100 schema-valid responses with no unexplained empty lists as a format check. Loop the step 3 check over your prompts; benchmarks/extraction shows the pattern. Before testing, label must-keep facts on held-out turns, including no-fact turns, and set minimum coverage and maximum unsupported-fact rates. Ship only when the framework-level run meets those targets.

Thinking mode off for extraction

For schema-constrained extraction, keep thinking off: it can consume the output limit before JSON starts.

Quantization

Use a 4-bit build; measure its extraction quality. Unsloth's bfloat16 (16-bit floating point) and 4-bit estimates (Numbers) are secondary, not file sizes or serving measurements.17 Unsloth says its 4-bit builds keep sensitive layers at higher precision.17 Ollama's default file is not always 4-bit: qwen3.5:2b is Q8_0 (step 1).

Plan on about 6.6 GB for Qwen3.5 9B with vision: the Q4_K_M file is about 5.6 GB, and the bfloat16 vision projector, unneeded for text-only writing, adds the rest. Ollama's MLX package (its Apple-silicon format) is 7.6 GB, not the GGUF size. Downloads exclude context buffers, so measure peak memory at your context size.19,20,21,22 From file sizes, not measured: on an 8 GB GPU stay with 2B to 4B models; use 9B on 16 GB or more.

Research note: sub-1-bit weights

Use the 4-bit builds above, not sub-1-bit weights. Samsung's LittleBit (NeurIPS 2025) and LittleBit-2 (ICML 2026) compress a model to 1.0 to 0.1 bits per weight with binarized low-rank factors and learned scales.23 It requires quantization-aware CUDA training, so finished checkpoints cannot be converted. Supported families are OPT, Llama, Phi-4, Qwen2.5, QwQ, Gemma 2 and 3, and Qwen3, but not Qwen3.5, under CC BY-NC 4.0, which bars commercial use. Not run here; paper accuracy tables unchecked.

Latency and why saves run in the background

In the Chapter 19 deployment (retain and recall calls, a 9B writer, an Apple silicon Mac), recall took about 2 seconds, a warm retain about 25 seconds and a cold service start about 2 minutes; the timings are unpublished.24 Mem0 first embeds the conversation and retrieves the ten nearest memories as context.2,25 In the CPU test (step 4), one Mem0 add took 68.6 seconds: 52.8 reading Mem0's own 8,226-token prompt at 155.7 tokens per second, 8.4 generating 62 tokens and 7.4 not itemized. The repeat add reused cached computation for the unchanged prompt prefix, evaluating only 125 tokens anew. Its 13.6 seconds does not predict unrelated saves. Queue saves and answer first.

Queued saves can overwrite newer corrections, duplicate facts on retry or revive deleted facts on replay. Chapter 17 covers ordering, idempotency and lasting deletes.

Plain recall skips the writer. Hindsight can prune results with a small "decision" model: it reports a 167 ms median on its workload, against 1 to 7 seconds for a main model call. On an Apple M1 Ultra it took 132 ms for prompts of about 240 tokens (36 requests) and 2.1 seconds for about 5,700 tokens (206 requests).26

Not yet tested here: purpose-trained memory writers (Hy-Memory)

Tencent's Hy-Memory-30B-A3B is trained for long-term memory writing, rather than general chat with an extraction prompt. It was not run. The card states no quantized size or hardware requirement; an untested estimate puts a 4-bit file near Inkling 2 Mini's 20 GB, beyond the 8 GB and 16 GB machines this chapter targets.

  • Released in October 2026, it has about 30 billion parameters, about 3 billion active per token. Its weights are Apache 2.0, read 20 November 2026.7,8
  • The card describes a drop-in writer for Mem0, MemOS and Hy-Memory, with transfer evaluated on EverMemOS, a framework held out of training; it selects facts and reconciles new evidence.7
  • The separate Hy-Memory framework, also Apache 2.0,41 supports Chat, Working and Coding pipelines, described in Chapter 16.9
  • The card reports a 55.49 overall score for this writer against 54.62 for Claude Opus 5. Tencent averages six metrics on 20% subsamples across four memory frameworks, changing only the writer; this is not extraction accuracy. Its coding metric averages two repository QA evaluations (Chapter 16).7

Not yet tested here: memory managers trained with rewards

Memory-R1 (27 August 2025, first paper version) trains a Memory Manager that chooses ADD, UPDATE, DELETE or NOOP and an Answer Agent that filters retrieved memories, by reinforcement learning on correct answers. It evaluates 7B and 8B backbones on LoCoMo, a long-conversation memory benchmark, with 152 training question-answer pairs and reports better answers than its reimplemented baselines, with no production reliability or 2B results.40 It trained on four 80 GB H100 GPUs and was not run. Chapter 16 compares other learned-memory approaches, including MemRL, which updates stored episodes' utility at run time with frozen weights.

Good for and not for

Good for

  • Personal or regulated memory that must not leave your network.
  • A save on every message, where a cloud call per turn is costly or not permitted.
  • A schema, such as preferences, entities and dates, that a grammar or JSON schema can enforce and that passes 100 of your own prompts.
  • Background and overnight work, where a 25-second save does not matter.
  • A Mac with 16 GB or more, or an 8 GB GPU running a 4B model, if peak use with your prompt and context leaves OS and embedder headroom.

Not for

  • Bulk-loading documents you have: embed them, since paraphrasing risks lost details (see the cost example).
  • Multi-hop recall answers and long synthesis. Use a larger or hosted model for those steps.
  • Writes that must be right first time with no review. Mem0's add-only pass makes a bad extraction stick,2 and the measured writers missed many reference facts.
  • Tool calling without testing both thinking modes: every model moved 8 to 12 points; 4B worsened (Numbers).
  • Graph extraction that produces many invalid edges; move that step to a bigger model.

Use cases

1Private assistant memory on a 16 GB Mac or an 8 GB GPU

Situation
A chat or voice assistant on a 16 GB Apple silicon Mac or 8 GB GPU keeps weeks of preferences and events off-cloud.
Why it fits
Gemma 4 E4B (4.5 GB estimated at Q4_0, including 20% overhead) led observed fact recall. E4B and Qwen3.5 4B are 8 GB GPU candidates; measure peak GPU use with your context and embedder.17,28 On 16 GB, Qwen3.5 9B (5.6 GB, text-only Q4_K_M) also supports tools.19,20 Hindsight lists local providers including Ollama, LM Studio and llama.cpp.4
Pair with
Queue saves, timestamp facts, keep raw transcripts and require a JSON schema on extraction calls; step 4 does not demonstrate that constraint. Chapter 07 covers sensitive content.

2Extraction on a CPU-only mini PC

Situation
A CPU home server saves a few agent memories hourly.
Why it fits
Small models run on CPU. A 2B model returned a schema-valid answer in 4.9 seconds with thinking off (warm model, step 2), and a Mem0 add took 68.6 seconds (step 4, using the step 3 server and step 1 embedder). That suits a queued job, not a live one.
Pair with
A job queue. The 2B writer covered only 34.3 percent of reference facts; where policy permits, skip live extraction and batch transcripts directly to a larger nightly writer (Chapter 17). 0.8B extraction is unmeasured.

3Nightly consolidation of a day's log

Situation
A nightly job deduplicates an agent's daily log and drops stale lines.
Why it fits
Letta's sleep-time design edits memory while the main agent is idle, so the slow call costs no waiting.6 A local run avoids per-call fees but occupies the machine.
Pair with
Keep raw episodes: a small model can overwrite a correct fact with a worse summary (operator judgment).

4When to pay for a hosted model

Situation
A product serves many users, answers multi-hop queries or loads history once.
Why it fits
Mem0's quickstart default is hosted, gpt-5-mini.1 Hosting removes local fit constraints; compare it with your local writer on your product's tool calls.
Pair with
If policy permits sending the question and retrieved facts off-device, host only the hard step, such as graph extraction or reflection; otherwise queue it for a larger local model or omit it.

Measured extraction quality

Tested Small writers rarely stored a wrong fact: precision was about 95 percent or better for most, but fact recall ranged from about a quarter to under 60 percent. The main risk is forgetting. Keep raw transcripts searchable and re-extract nightly with a larger writer where policy permits (use cases 1 to 3).

The run made 9,000 requests across ten arms: the seven writers below, a repetition-penalty arm and two Qwen2.5-Coder files (Chapter 07). Each arm used 300 public long-conversation benchmark turns (LoCoMo and LongMemEval), three seeds, Q4_K_M files and an Apple M3 Ultra, 96 GB. Pooled per-arm precision divides supported facts by written facts; fact recall divides covered references by all references. Invalid or empty responses lower fact recall, not precision. The implementer wrote reference facts without independent review; update and contradiction reconciliation were not measured.

Worked cost example: 7,700 existing passages

Pushing 7,700 passages through a 25 s retain call takes 192,500 s, 53.5 hours, on one worker; at the CPU Mem0 add's 68.6 s, 146.7 hours. Embedding is far smaller: a CPU text-embedding server embedded 100 short texts in 0.544 seconds (Chapter 03), so 7,700 take about 42 seconds, a floor because real passages are longer.

import json, subprocess, sys, time, urllib.error, urllib.request

def logs(container):
    subprocess.run(["docker", "logs", "--tail", "30", container], timeout=10)

def wait_ready(url, container):
    for attempt in range(60):
        try:
            with urllib.request.urlopen(url, timeout=2) as response:
                json.load(response)
            return
        except (urllib.error.URLError, TimeoutError, OSError, ValueError):
            if attempt < 59:
                time.sleep(2)
    print("STOP: endpoint not ready:", url, file=sys.stderr)
    logs(container)
    raise SystemExit(1)

def request_json(req, container):
    try:
        with urllib.request.urlopen(req, timeout=600) as response:
            return json.load(response)
    except (urllib.error.URLError, TimeoutError, OSError, ValueError):
        logs(container)
        raise

if __name__ == "__main__":
    wait_ready(*sys.argv[1:])

Gotchas

Gotcha: thinking eats the answer

Despite the 2B card, both tested runtimes thought by default, and step 3 exhausted its output limit on reasoning (fix: Thinking mode).13,18

Gotcha: the prompt is bigger than the conversation

mem0ai==2.2.1 sent 8,226 tokens to the model for a two-sentence chat, and a 4,096-token window failed with HTTP 400. Size the window for the framework's prompt.

Gotcha: Mem0 keyword and entity boosts do not widen the candidate set

In mem0ai==2.2.1 the keyword (BM25) and named-entity signals only re-rank semantic candidates, so they cannot rescue an exact identifier the semantic search missed (Chapter 13).2,37

Open questions

  • Extraction quality across other hardware, quantizations and schemas remains unmeasured here.
  • 4-bit memory for the official Qwen3.8 27B: the card does not state it.

Verdict

Verdict: local for new conversations, embeddings for old documents

Pick a small local model when memory is private, saves run in the background, and your framework run meets the format and fact-coverage targets above. Start with Gemma 4 E4B: on the general schema and 96 GB machine it led fact recall with lower median latency than Qwen3.5 9B. The printed end-to-end walkthrough uses Qwen3.5 2B. Measure peak memory and fact coverage with your framework prompt: a 9B model at 4-bit is the 16 GB Mac candidate, a 4B model or E4B the 8 GB GPU candidate. If you also need tools, compare both on your tool calls (Qwen3.5 9B scores 66.1 on its card; E4B was not tested). Avoid the empero-ai 4B and 9B distills. Disable extraction thinking; test thinking for tools. Updates and contradictions were not tested; check them before trusting background saves.

Embed existing documents instead (Chapter 03). Use a larger or hosted model for multi-hop reads or graph extraction. For uncensored variants, see Chapter 07; for case studies, Chapter 21 picks Qwen3.5 9B with a 2B vision worker for a one-owner business; Chapter 22 splits a 27B staff lane from a 9B phone lane.
