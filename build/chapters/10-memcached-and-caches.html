Memcached and the cache layer

A cache keeps recomputable answers, vectors and prefixes so an agent can reuse work.

Maturity

Shipped

Setup effort

1 of 5

Running cost

1 of 5

Best for

Agent apps that repeat prompts, embeddings or tool calls, with a durable store behind them.

What it is

Agents repeat prompts, embeddings and document reads. A cache provides fast, disposable copies, avoiding repeat costs. Memcached stores these copies under keys, in RAM by default, until expiry or eviction.12

Keep facts elsewhere. This chapter covers Memcached, response, semantic, embedding and tool-result caches, provider prompt caching and local inference-level reuse.

Terms new in this chapter

Prompt prefix
A prompt’s start; requests share one when their first tokens match.
KV cache
Attention keys and values for a prompt, unrelated to key-value stores. Reuse skips re-reading the prefix.
Semantic cache
Matches questions by meaning, not exact text.
Cache key, authorization scope
A key names a stored value; authorization scope identifies who may reuse it.
Cache control
A provider marker or option selecting prompt blocks for reuse.
Slab class, CAS
Memcached pools similar-sized items in slab classes and evicts within each. CAS (compare-and-swap) uses a token from a versioned read; writes with stale tokens fail.
Hit, miss, TTL, eviction
A hit finds a usable entry; a miss does not. TTL limits serving time; eviction drops entries early for space (Chapter 09).

How it works

Applications manage Figure 1’s first four layers. Memcached serves exact-key lookups; semantic lookup needs a vector-capable store such as Redis. Providers or inference servers manage the last two.

The six layers

LayerWhat it stores and matches onLifetime guidance
Exact-match response cacheA finished answer keyed by hashed model, parameters, prompt, authorization scope and data version.Minutes to hours. Bump the data version on write.
Semantic cacheAn answer matched by question embedding within a distance threshold (lower is stricter). Examples: GPTCache,4 RedisVL,5 Redis,6 Amazon ElastiCache.7Short, and only after hit precision is measured.
Embedding cacheA vector, keyed by pinned model revision, preprocessing settings and text hash.Long or none. Changing any of these changes the key.
Tool-result cacheRead-only tool output keyed by tool, arguments and authorization scope.Bound the TTL by permitted staleness. Cache user-dependent reads only with authorization scope and data version in the key.
Provider prompt cacheProvider-held state for a repeated prefix, excluding answers; re-reads cost less.Anthropic’s documented default: 5-minute retention. Prices and thresholds under Numbers.8
Inference-level reuseThe engine keeps or restores prompt-prefix KV state.Until the engine evicts it or the file is deleted.

Memcached keys and defaults

Memcached stores opaque bytes under keys. set writes a value and get reads it back. It has no data structures or vector search. Keys are limited to 250 bytes, and the protocol forbids whitespace and control characters.

Hash prompts, validate keys client-side and avoid tabs/control bytes even if accepted.1

Flash, restart and expiry are cache features

  • Extstore moves colder values to flash and keeps keys and the hash table in RAM.19
  • Warm restart keeps items in a memory-mapped file, recording metadata at graceful shutdown. It requires a stable clock; missed sets/deletes during restart can leave stale entries. The cache starts empty if -m, -I, slab chunk sizes, -C (CAS) or slab reassignment differ from the previous run. Extstore is documented as incompatible.3
  • Expiry up to 2,592,000 seconds (30 days) is relative; larger values are Unix timestamps. Eviction reclaims least-recently-used items within each slab class; watch the per-class evicted counters before raising memory.12

Local servers

  • llama.cpp server: --slot-save-path plus POST /slots/{id}?action=save or restore saves or restores a slot’s KV state (one server-side conversation context).14 Saved prompts are readable; treat files as sensitive.
  • LM Studio MLX engine: loads previously seen prompt KV state from disk; see the cited configuration guide.15
  • oMLX: persists KV cache blocks to SSD; see its configuration guide (checked 20 November 2026).16
  • vLLM: reuses matching prompt-prefix KV state to cut prompt-processing work.17
  • LMCache (repository checked 20 November 2026): a self-run, Apache-2.0 layer that offloads KV state from GPU memory to CPU RAM, local disk or remote backends and shares it across requests and engines. It saves prompt-processing work, not provider billing.18

Good for and not for

Good for

  • Identical requests permitting replay: FAQ questions from, or normalised to, a fixed list. Repeating templates around changing records suit provider prompt caching.
  • Embedding the same text repeatedly: re-indexing, retries, repeated chunks.
  • Read-only tool calls repeated within a short window.
  • Cheap shared caching across app servers already running Memcached.
  • Long stable system prompts or document prefixes, through provider prompt caching.

Not for

  • Agent memory: facts about a user, decisions, task state. Use a durable store (Chapter 08; Chapter 11 for embedding retrieval).
  • Answers that depend on per-user state when the key cannot carry that scope.
  • Matching by meaning: Memcached alone has no vector search. Use RedisVL or GPTCache with strict thresholds.
  • Medical, legal or financial actions where a stale hit does harm.
  • Persistence, data structures or queue semantics. Use Redis or Valkey.

Use cases

1FAQ bot with repeated questions

Situation
A support bot pays per model call for a few hundred recurring questions through one template.
Why it fits
An exact-match response cache uses the layers-table key with fixed public scope and FAQ version as data version. Each repeat needs one get for a listed or normalised question; hashing keeps keys under the 250-byte limit.1
Pair with
A minutes-to-hours TTL; bump the data version when answers change. Skip it for questions that depend on the signed-in user.

2Re-ingesting a document library

Situation
A nightly job re-embeds all 20,000 chunks though few changed.
Why it fits
For repeatable embeddings, store vectors by text hash, pinned model revision and preprocessing settings. Only new or edited chunks need embedding (figures under Numbers).
Pair with
A vector-store index (Chapter 11). Flushing the cache forces re-embedding.

3Agent that keeps calling a read-only tool

Situation
A research agent repeatedly fetches slow or rate-limited exchange rates or documentation each hour.
Why it fits
Key tool results by tool name, arguments and authorization scope. Set TTL to accepted staleness: minutes for exchange rates, hours for documentation.
Pair with
State-dependent read keys require authorization scope and relevant data version. Keep the authoritative copy elsewhere. Never cache state-changing calls; a write must bump the changed data’s version.

4Long system prompt on a hosted model

Situation
A coding agent’s repeated long instructions and tool definitions dominate its input bill.
Why it fits
Anthropic bills a cached prefix at a fraction of base input, from 0.025x for Fable/Mythos 5.2 to 0.1x for Haiku 5.5 (per-model prices are on the pricing page).8 Memcached is not involved.
Pair with
Usage fields cache_read_input_tokens and cache_creation_input_tokens; nonzero reads on the second call confirm reuse.

5Local agent on llama.cpp with a big prefix

Situation
A local agent reloads a large prompt each session, delaying its first answer.
Why it fits
llama.cpp can save a slot's KV state to disk and restore it, reusing a compatible prefix. Check timings.cache_n and prompt_n to confirm the reuse, and time it on your hardware.14
Pair with
Restricted permissions on the save folder.

6Pilot of a semantic cache

Situation
Support teams want paraphrased questions to share answers, but "Cancel my order" and "cancel my subscription" must not.
Why it fits
RedisVL’s SemanticCache separates near matches with a distance threshold, TTL and metadata filters.5
Pair with
Hit precision measured on real logs before launch.

What a hit saves, and sizing

A cache tells the model nothing new; it saves work by layer:

  • Exact-match response cache: a hit costs one lookup and zero model calls or tokens.
  • Embedding cache: a hit makes no embedding call, a miss one.
  • Semantic cache: a lookup generally embeds the query even on a hit.5
  • Provider prompt caches and inference-level reuse: they still generate output tokens and skip only reusable input processing.17

Capacity estimate: payload RAM = users × entries/user × bytes/entry. At 1,000 users × 100 entries × 8 KiB, that is about 781 MiB, while 256 MiB item memory (-m 256) fits at most 32,768 such payloads, fewer after keys, item headers and slab rounding. All 100,000 cannot coexist; expect evictions.

Watch the stats command (get_hits, get_misses, evictions) and, per slab class, stats items: rising evictions with a falling hit rate signal a capacity problem.2

Worked example: embedding cache on a re-ingest (counts are assumed)

RunEmbedding-model callsCache hits
First ingest, 20,000 chunks20,0000
Re-ingest, 400 chunks edited40019,600

Re-ingest makes 98 percent fewer embedding calls; the third misses on model-revision change. Memory cost: 20,000 vectors of 1,536 float32 numbers take about 117 MiB raw, before per-item overhead (bytes per vector: Chapter 00). The walkthrough stores float32 bytes but returns original floats on misses, rounded floats on hits; its fixture hides the difference. An undersized cache drops items for re-embedding: slower, never wrong.

  2. Write, read, test limits and reuse a vector

    Save the file below as /var/tmp/memlab-10/run/memcache.py. Acknowledged writes (default_noreply=False) expose server errors. Real revision keys also need dimensions and normalization alongside revision and preprocessing. Write mode checks size rejection and vector reuse; read mode checks saved values in a fresh process within 60 seconds. Embedding TTL is a lab bound; use long or no TTL as advised above.

    pythonmemcache.pyTested
    import hashlib, json, struct, sys, time, uuid
from pymemcache.client.base import Client
from pymemcache.exceptions import MemcacheError, MemcacheServerError

options = dict(default_noreply=False, connect_timeout=1, timeout=1, ignore_exc=True)
c = Client(("127.0.0.1", 39100), **options)
c2 = Client(("127.0.0.1", 39101), **options)

def response_key(version):
    fields = ["demo-model-v1", {"temperature": 0}, "FAQ hours?", "public", version]
    return hashlib.sha256(json.dumps(fields, sort_keys=True).encode()).hexdigest()

if sys.argv[-1] == "read":
    assert c.get(response_key("faq-v1")) == b"summary"
    assert c.get("month") == b"retained"
    print("fresh-process read OK")
    c.close()
    c2.close()
    sys.exit(0)
print("set/get TTL", c.set(response_key("faq-v1"), "summary", expire=60),
      c.get(response_key("faq-v1")))
assert c.get(response_key("faq-v2")) is None
print("version bump: MISS")
expiry = int(time.time()) + 31 * 24 * 60 * 60
assert c.set("month", "retained", expire=expiry)
print("absolute expiry", c.get("month"))
large_key = "large:" + uuid.uuid4().hex
try:
    c.set(large_key, b"x" * (1024 * 1024 + 1))
except MemcacheServerError as e:
    assert e.args[0] == b"object too large for cache"
    print("default rejection", type(e).__name__, str(e))
else:
    raise AssertionError("oversized item accepted")
assert c2.set("check", b"ok")
print("raised limit", c2.set(large_key, b"x" * (1024 * 1024 + 1)),
      len(c2.get(large_key)))

def embedding_cache(revision, text, compute):
    key = hashlib.sha256((revision + "\0" + text).encode()).hexdigest()
    cached = c.get(key)
    if cached is not None:
        return list(struct.unpack("<" + "f" * (len(cached) // 4), cached))
    vector = compute(text)
    try:
        if not c.set(key, struct.pack("<" + "f" * len(vector), *vector), expire=3600):
            print("cache set failed", file=sys.stderr)
    except (OSError, MemcacheError) as error:
        print("cache set failed:", error, file=sys.stderr)
    return vector

def must_not_run(text):
    raise RuntimeError("must not compute")

revision = "demo-v1:prep1:" + uuid.uuid4().hex
print("cache miss", embedding_cache(revision, "hello", lambda text: [1., 0., 0., 0.]))
assert embedding_cache(revision, "hello", must_not_run) == [1., 0., 0., 0.]
print("cache hit", embedding_cache(revision, "hello", must_not_run))
c.close()
c2.close()

  3. Reject an inappropriate semantic hit

    RedisVL takes a maximum cosine distance in [0,2], so lower is stricter; a similarity API takes a minimum, so higher is stricter. Save this as /var/tmp/memlab-10/run/semantic.py. The distance formula assumes the cached vector is the unit x-axis vector. The third query is from another tenant, so the scope check rejects it despite its small distance; production must also check intent.5

    pythonsemantic.pyTested
    from math import sqrt

# Synthetic vectors: demonstrate a gate, not embedding-model quality.
cached = {"query": "Cancel my order", "vector": [1., 0.],
          "scope": "tenant-a:policy-v1", "answer": "Use order cancellation."}
queries = [
    ("Please cancel the order", [0.999, 0.045], "tenant-a:policy-v1", True),
    ("Cancel my subscription", [0.98, 0.20], "tenant-a:policy-v1", False),
    ("Please cancel the order", [0.999, 0.045], "tenant-b:policy-v1", False),
]
accepted = correct = 0
checks = []
for text, vector, scope, expected in queries:
    distance = 1 - vector[0] / sqrt(sum(x*x for x in vector))
    hit = scope == cached["scope"] and distance <= 0.01  # LOWER is stricter
    checks.append(hit == expected)
    accepted += hit
    correct += hit and expected
    print(text, scope, f"distance={distance:.4f}",
          cached["answer"] if hit else "MISS: compute fresh answer")
print(f"hit precision: {correct}/{accepted}")
assert all(checks), "unexpected semantic decision"

Gotchas

Gotcha: unsecured defaults

Authentication and TLS are off by default. Bind privately; firewall or tunnel access from untrusted hosts.

Gotcha: the cache must not be the only copy

Write the source of truth to a durable store first, so a miss is only slower, never wrong.

Gotcha: stale or cross-user answers

Include authorization scope, model, parameters, prompt and data version in every response key. Memcached cannot delete by prefix. Commit data and its version together; fill from the same snapshot under that version. New-version readers cannot hit old entries, which age out. Missing scope risks cross-user answers; missing versions risk stale advice.

Gotcha: semantic false hits

Questions that read alike can need opposite answers. Tighten the threshold (walkthrough step 3), gate by metadata, and measure hit precision on real logs first.5

Gotcha: prompt-cache misses are silent

Anthropic documents silent misses below the minimum prefix length; check usage counters. An entry is available only after the first response starts, so parallel requests on a cold prefix can all miss; start one first, then fan out.8

Gotcha: a stampede on one key

Popular-entry expiry can send many workers to the model together. Within one process, share one in-progress fill per key. Across processes, Memcached add creates a short-lived lease only if absent; only the successful caller fills. On a failed add, back off and recheck. Size the lease for slow fills, and tolerate duplicate work if one outlasts it.

Verdict

Verdict: use a cache, never as memory

Add a cache layer when prompts, texts or tool calls repeat. Count repeated requests, unchanged chunks and shared prefixes within provider retention; measure hit precision and savings per hit. Adopt layers whose savings exceed lookup, write and storage costs. Include full authorization scope in response keys. Choose Memcached for existing installations or exact-match bytes with TTLs; otherwise reuse Redis or Valkey.

For shared state or persistence choose Redis or Valkey (Chapter 09); for semantic matching choose a vector index (Chapter 11). Keep required facts durably (Chapter 08 or 11). Chapter 22 applies these keys to a regulated office: actor, patient, task, policy and data version.
