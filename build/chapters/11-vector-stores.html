Dedicated vector stores

Searches vectors and metadata, with indexes and storage for large or multi-vector memory collections.

Maturity

Shipped

Setup effort

2 of 5

Running cost

3 of 5

Best for

Tenants, large corpora or multi-vector pages outgrowing general databases.

What it is

A dedicated vector store is a database that finds memories by meaning. It saves each memory as an embedding (Chapter 03), text and metadata; a query vector retrieves the nearest vectors and their metadata.

General database vector columns do this too. In pgvector, a scan of every eligible vector is exact, and a query through a graph index (HNSW) or cluster index (IVFFlat) is approximate. PostgreSQL also offers ACID transactions and joins with ordinary tables (Chapter 08).1 Dedicated stores add search-focused filtering and object-storage designs.2,3 Coverage includes servers, services, embedded stores and libraries; sqlite-vec appears briefly here, fully in Chapter 12.

Terms new in this chapter

Payload
Metadata saved beside a vector, such as a user id or timestamp.
Collection, namespace
A named group of records; isolation and filtering guarantees vary by store.
MaxSim
Late-interaction models (Chapter 04) emit a vector per image patch or token. MaxSim sums each query vector's best page-vector similarity; rank pages by decreasing score.

Approximate nearest neighbor (ANN) indexes skip vectors, trading recall@k (share of true top k returned) for speed. Chapters 03 and 05 explain embeddings, quantization and hybrid ranking. User id is the examples' tenant key.

How it works

Save embedded memories, text and metadata. Embed questions, search the permitted tenant and put the top k hits into the prompt.

Index families in plain words

FamilyHow it worksWhat it trades
FlatCompares the query with every vector.Exact results, but cost grows linearly with the corpus.
IVFSplits vectors into clusters and scans only the few nearest clusters.Faster than flat, but misses neighbors in unscanned clusters.
HNSWA layered near-neighbor graph, mostly in RAM, searched by node-to-node hops (below).4Fast and accurate, but memory-hungry.
Disk graphs (DiskANN)A graph designed for SSD.5Handles data larger than RAM, with slower hops.
Scalar and product quantizationShrink each vector to fewer bits or to a short code.4Less memory, some recall lost.
Binary quantizationKeeps one bit per dimension, with full vectors on disk to rerank candidates.6Up to 32x smaller than float32, but it needs reranking to keep recall.

Milvus lists DiskANN and HNSW among its index options.5

HNSW parameters

Conventional HNSW names are M, efConstruction and efSearch. In pgvector, m limits links per node per layer (layer 0 allows twice that). Graph links add to raw-vector storage; doubling m roughly doubles this overhead. ef_construction sets the build candidate-list size (higher: better recall, slower builds). hnsw.ef_search sets the query candidate-list size (higher: generally better recall, higher cost). Qdrant calls them m, ef_construct and hnsw_ef: defaults 16, 100 and 100. pgvector defaults are m 16, ef_construction 64 and hnsw.ef_search 40. A non-iterative pgvector scan also caps returned rows at hnsw.ef_search; iterative scans (below) continue.1 Tune query breadth first (pgvector hnsw.ef_search; Qdrant hnsw_ef), measuring latency and recall@k against exact filtered search (Numbers).

Metadata filtering: before, during or after the search

Pre-filtering restricts candidates before scoring, often scanning matches directly. in-graph filtering checks predicates during traversal. post-filtering drops mismatches afterward, potentially returning fewer than k results. Chapter 08 demonstrates pgvector HNSW post-filtering. Qdrant filters in the graph, or scans exactly when few points match; check other stores separately. In Qdrant, tenant payload indexes add tenant-specific graph links. Create them before ingest; filtering improves at the cost of slower builds and larger graphs.2

In pgvector, filtering follows the index scan. If 10% of candidates match the tenant, a non-iterative scan with hnsw.ef_search = 40 returns about four matching rows on average. Set hnsw.iterative_scan to relaxed_order or strict_order (default: off) to continue until enough rows match, index exhaustion or a resource limit (hnsw.max_scan_tuples or hnsw.scan_mem_multiplier). Relaxed order may slightly misorder distances. Selective filters can still hit that limit (Numbers). Use partial indexes for a few predicates; for many tenants, consider PostgreSQL partitions, Qdrant graph filtering or store namespaces.1,2 Qdrant filters support nested AND, OR and NOT clauses.2

Hybrid search

Vector search struggles with exact names, ids and rare words. Hybrid search blends keyword rankings such as BM25 with vector rankings, usually through reciprocal-rank fusion (Chapter 05). Qdrant 1.20 documents BM25 ranking on a full-text index over stored text, so the client builds no sparse vectors; the walkthrough instead shows unfused LanceDB searches.7

Good for and not for

Do you need one at all

Stay on PostgreSQL until filtered recall or p95 misses your target, the index exceeds RAM, or multi-vector pages require reconsideration. Record exact in-tenant top-k ids and latency; if too slow, test ANN against those ids and remeasure latency. pgvector gives no switching threshold.1

Good for

  • Selective filters: tenant-scoped search prevents other tenants consuming candidate budgets. Measure recall against exact in-tenant search.
  • Corpora too large for one machine's RAM, using disk graphs, quantization or object storage.
  • Multi-vector pages: hundreds of vectors per document.
  • Hybrid keyword and vector queries in one API.
  • Teams that want a managed service for index tuning.

A server or managed store is not for

  • One user's local notes: use an embedded store (use case 1) or SQLite (Chapter 12).
  • Transactional joins with relational data: use PostgreSQL (Chapter 08).
  • Offline devices: use embedded stores (use case 5).

Use cases

1Local memory for a desktop or command-line agent

Situation
A laptop agent needs persistent semantic search over thousands of notes.
Why it fits
Chroma and LanceDB persist local directories in process; LanceDB is pre-v1.19,20 For one .db file, use dependency-free C sqlite-vec (Chapter 12; pre-v1).23 Pin versions.
Pair with
Chapter 12 for SQLite. Avoid a second daemon for one user.

2Millions of memories across many tenants

Situation
A hosted assistant serves mostly small tenants; queries must stay within their tenant.
Why it fits
Qdrant filters during the graph search;2 Numbers compares filtered recall with unequal search budgets. For RAM-resident Qdrant, share one collection; on turbopuffer and Pinecone, give each tenant a namespace, since idle namespaces sit in object storage, not RAM.3,15
Pair with
For tenant-only Qdrant, mark the tenant keyword index is_tenant; m=0 skips the global graph and payload_m=16 builds tenant-specific links. Retain a global graph for fast cross-tenant searches.26 Avoid post-filter-only designs for selective filters.

3Very large corpora

Situation
Years of cold documents exceed one machine's RAM.
Why it fits
Milvus is distributed with many index types.5 S3 Vectors suits cold tiers, and AWS says infrequent queries return in under one second (a vendor claim, not run here).27
Pair with
Quantization with full-vector reranking. Avoid single-node RAM-only HNSW at this size.

4Multi-vector pages from Chapter 04

Situation
Scanned PDFs use a late-interaction model such as ColQwen2: up to 768 visual patches plus text tokens.28
Why it fits
Qdrant supports late interaction with a MaxSim comparator (its API calls these multivectors). The walkthrough queries two stored synthetic pages.29
Pair with
Shortlist before MaxSim reranking. Budget 197 GB raw per million pages (Numbers).

5Offline or edge use

Situation
A field device or Raspberry Pi needs memory without reliable networking.
Why it fits
Milvus Lite targets laptops and edge devices with Python.21 usearch keeps a small footprint.25 sqlite-vec (Chapter 12) runs on Linux, macOS, Windows, WASM and Raspberry Pi.23
Pair with
Sync to a server later. Avoid managed-only services, which have no offline mode.

Ground truth is exact tenant-scoped PostgreSQL search; Qdrant exact=True matched all 200 queries at each filter. Qdrant used m=16, ef_construct=100, not the tenant-only layout above. Unequal search breadth (pgvector 40, Qdrant 100) prevents isolating filter placement. Qdrant may scan small tenants exactly. One build per store; no throughput claim. Shared memory/disk pressure invalidate latency comparisons; higher scan limits trade time for recall.

The selective filter has 20 rows. Default iterative limits include hnsw.max_scan_tuples=20,000. Partial indexes cover queried predicates; per-tenant maintenance was not tested. For small tenants, benchmark indexed tenant lookup with exact scoring.

Tested: in a local MongoDB Atlas container with 100,000 384-dimension vectors, CPU only, one build per mode, index files shrank 3.221x with scalar quantization and 15.680x with binary. Only unquantized files include full vectors; quantized files exclude reranking vectors, so total disk savings are smaller. Graph links do not shrink. These ratios neither measure MongoDB's RAM metric nor verify Atlas Required Memory or peak RAM.

Scope and scale

Retrieval supplies context without judging memories' truth. Latency includes embedding and store time; the walkthrough tests correctness only. Retrieving a new memory in the same turn requires searchable writes; Qdrant scripts use wait=True. Elsewhere, probe a same-tenant write then read; record time-to-visible. Beyond the turn budget, read the write store or wait explicitly.

  • Per write or read (one unbatched item): one embedding call plus an upsert or a search. Five 200-token hits add about 1,000 input tokens to the answer (estimate).
  • Capacity: see the Chapter 00 sizing reference. 1,000 users x 1,000 memories at 1536 dimensions in float32 is the 6.1 GB row above; 100,000 users need 614.4 GB, and indexes, text and replicas add more (estimates). A 16 GB RAM budget cannot hold three million such vectors uncompressed (18.432 GB); multi-vector pages hit it sooner.
  • Concurrency: 100 agents making one lookup per second need 100 searches and 100 query embeddings per second, before batching or caching.

Measure RAM-resident HNSW memory at target size and p95 at target concurrency. Measure object-backed cold and warm store p95 separately from embedding time. If recall misses its target, test filtering or search breadth; if RAM is exceeded, trial disk-backed search. No universal row threshold applies. Chapter 10's cache handles repeated lookups.

  2. Qdrant: save two memories and search for one user

    Write creates a collection and two points; a fresh process reads through a tenant-filtered query_points.

    pythonqdrant_test.pyTested
    import sys
from qdrant_client import QdrantClient, models

c = QdrantClient(url="http://127.0.0.1:39110")
if sys.argv[1] == "write":
    c.create_collection(
        "memories",
        vectors_config=models.VectorParams(
            size=4, distance=models.Distance.COSINE),
    )
    c.create_payload_index("memories", "user_id",
        field_schema=models.KeywordIndexParams(
            type="keyword", is_tenant=True), wait=True)
    c.upsert("memories", wait=True, points=[
        models.PointStruct(id=1, vector=[1., 0., 0., 0.],
            payload={"user_id": "alice", "content": "likes databases"}),
        models.PointStruct(id=2, vector=[0., 1., 0., 0.],
            payload={"user_id": "bob"}),
    ])
    sys.exit(0)
only_alice = models.Filter(must=[models.FieldCondition(
    key="user_id", match=models.MatchValue(value="alice"))])
res = c.query_points("memories", query=[1., 0., 0., 0.],
    query_filter=only_alice, with_payload=True, limit=3)
assert [p.id for p in res.points] == [1]
for p in res.points:
    print(p.id, p.score, p.payload)

  5. Qdrant: store multi-vector pages and query with MaxSim

    Multi-vector fields require Qdrant 1.10.0+. Size counts dimensions per vector, not vectors per page. Each query vector matches its best page vector, so page-a scores 1 + 1 = 2 and page-b scores 0 + 0 = 0.29

    pythonmaxsim_test.pyTested
    import sys
from qdrant_client import QdrantClient, models

c = QdrantClient(url="http://127.0.0.1:39110")
if sys.argv[1] == "write":
    c.create_collection(
        "pages",
        vectors_config={
            "dense": models.VectorParams(size=4, distance=models.Distance.COSINE),
            "patches": models.VectorParams(
                size=4, distance=models.Distance.COSINE,
                multivector_config=models.MultiVectorConfig(
                    comparator=models.MultiVectorComparator.MAX_SIM),
                hnsw_config=models.HnswConfigDiff(m=0),
            ),
        },
    )
    # Each page has 16 patch vectors; every vector has 4 dimensions.
    page_a = [[1., 0., 0., 0.], [0., 1., 0., 0.]] * 8
    page_b = [[0., 0., 1., 0.], [0., 0., 0., 1.]] * 8
    c.upsert("pages", wait=True, points=[
        models.PointStruct(id=101,
            vector={"dense": [1., 0., 0., 0.], "patches": page_a},
            payload={"page_id": "page-a"}),
        models.PointStruct(id=102,
            vector={"dense": [0., 0., 1., 0.], "patches": page_b},
            payload={"page_id": "page-b"}),
    ])
    sys.exit(0)
saved = c.retrieve("pages", ids=[101, 102], with_vectors=True)
assert len(saved) == 2
assert all(len(p.vector["patches"]) == 16 for p in saved)
query = [[1., 0., 0., 0.], [0., 1., 0., 0.]]
hits = c.query_points("pages", query=query, using="patches", limit=2,
    prefetch=models.Prefetch(query=[1., 0., 0., 0.], using="dense", limit=2),
    search_params=models.SearchParams(exact=True),
    with_payload=True).points
assert [p.id for p in hits] == [101, 102]
assert [round(p.score, 6) for p in hits] == [2., 0.]
for p in hits:
    print(p.payload["page_id"], p.score)
c.close()
    textTested
    page-a 2.0
page-b 0.0

    m=0 disables HNSW here, since a graph over hundreds of patch vectors per page adds memory and ingestion work, and exact=True scores the prefetched pages exactly. MaxSim work grows with shortlisted pages, query vectors, page vectors and dimensions.31

    Dense prefetch shortlists pages; MaxSim reranks their patches with HNSW disabled. Both toy pages enter in final order: scoring is verified, a ranking reversal is not. Shortlisting saves scoring work but cannot recover first-stage misses.31

Gotchas

Gotcha: churn and traps

  • Pre-v1 components change APIs. sqlite-vec's docs site labels v0.1.10-alpha.4 but its latest GitHub release is v0.1.9: pin one.
  • LanceDB's create_fts_index is deprecated as of 0.25.0, though online examples still show it.
  • A client-supplied filter is not authentication; derive it from the authenticated tenant.

Migration and lock-in

Keep stable ids, tenant metadata, model/preprocessing revisions and embedding inputs; for scans, keep PDFs and page mappings or images alongside extracted text. Snapshot consistently, record the change-log position, load the target and compare recall@k on identical queries. Replay subsequent upserts and deletes in order; pause writes, drain the log, compare per-tenant counts, verify deleted ids are absent and switch. Keep the old store read-only until acceptance; rollback is a config change only while writes stay paused. Retain the log after writes resume. For rollback, pause writes, replay post-cutover upserts/deletes into the old store, verify catch-up and switch back. Re-embed when the model changes (Chapter 03). Milvus Lite 3.x cannot open a 2.x .db in place.21

Verdict

Verdict: use one when filters, tenants or size force it

Pick a dedicated store when PostgreSQL misses product recall and p95 targets. Budget store time within the turn; measure recall against exact filtered results. For MaxSim, shortlist densely, then trial native reranking if application reranking misses that deadline. Qdrant, Chroma and LanceDB passed toy tests; filtered recall used synthetic vectors. Weaviate structured filters, turbopuffer and Pinecone namespaces, Milvus at scale and S3 Vectors remain untested.

Avoid server stores for single-file notes (Chapter 12) or relational joins (Chapter 08). Chapter 23's homebuilder starts on pgvector, reconsidering for page multi-vectors.
