One Postgres database holds facts, vectors and keywords for one filtered, ranked memory query.

What it is

pgvector adds embedding types (Chapter 03) and nearest-neighbour indexes to PostgreSQL for similarity search.1

Agent memory uses episodes rows for events and memories rows for facts and summaries, each with an embedding. One backup, permission model and query language cover keyword search, permissions and transactions.

Memory, embedding, audit and outbox rows (pending deliveries) commit or roll back together, and reads can join users and permissions while ranking. Framework support (Chapter 13): LangGraph ships PostgresSaver and PostgresStore,2,3 Mem0 has a pgvector provider,4 and Hindsight uses Postgres with pgvector as its primary storage backend.5

Terms used in this chapter

HNSW
Hierarchical Navigable Small World, a layered-graph approximate-search index (Chapter 00). Chapter 11 compares index families.
ef_search
Candidate-list size per HNSW query: higher means better recall, slower queries.
Recall@10, RRF
With at least ten eligible rows, recall@10 is the overlap of returned and exact top tens under identical filters, divided by ten. Reciprocal rank fusion (RRF) merges ranked lists (Chapter 05).
IVFFlat
pgvector's clustered-list index: probes sets how many clusters (lists) a query searches, trading speed for recall. It learns list centres from existing rows.
tsvector, GIN
tsvector holds searchable words; GIN indexes them for fast matching.
RLS
Row-level security. Policies control which rows a role sees.

How it works

The application commits raw turns to episodes. Fact extraction, often a model call (Chapter 06), produces memories. After extraction and embedding succeed, one transaction commits each memory, its vector and any audit or outbox row, with index updates. Never hold a transaction open across model calls.

Reads embed the question with the same model. One SQL statement filters user and validity, merges vector-distance and keyword rankings, and returns prompt rows. The walkthrough checks memory timestamps valid_from <= now() and valid_to IS NULL for current facts. For future start or end dates, test valid_from <= :as_of AND (valid_to IS NULL OR :as_of < valid_to) in both branches; the current-row partial index cannot cover this predicate.

Types and distance operators

pgvector adds three column types (vector, halfvec and sparsevec) and supports binary-distance search on PostgreSQL's built-in bit type. Its distance operators are <-> for L2 distance, <#> for negative inner product, <=> for cosine distance, <+> for L1, <~> for Hamming and <%> for Jaccard.1 Index use requires LIMIT and an ORDER BY matching the operator class (e.g. <=> with vector_cosine_ops); the planner may prefer exact scan and sort.

TypeUseLargest indexable size
vectorThe default dense embedding column.2,000 dimensions
halfvecDense embeddings that need an index above 2,000 dimensions.4,000 dimensions
bitBinary vectors, for example from binary_quantize with Hamming distance.64,000 dimensions
sparsevecSparse vectors that store only non-zero elements.1,000 non-zero elements

These are the README's index caps.1 Tested: each HNSW cap was accepted and cap+1 rejected, two boundary cases per type. Above 2,000 dimensions (e.g. 3,072), HNSW needs halfvec or dimension reduction. Alternatively, use CREATE INDEX ON memories USING hnsw ((embedding::halfvec(3072)) halfvec_cosine_ops) and order by embedding::halfvec(3072) <=> $1::halfvec(3072).

Good for and not for

Good for

  • Existing Postgres teams adding memory tables.
  • Memory writes committing with business data and audit.
  • Queries mixing user/validity filters, keyword rank and vector rank.
  • RLS-enforced user isolation (one tenant = one user_id).
  • Exact search within budget (tested: 37.242 ms median, 100,000 384-dimension rows, 2 CPUs), or HNSW meeting recall targets.

Not for

  • Tuned queries missing p99 targets: compare VectorChord, pgvectorscale and dedicated stores (Chapter 11).
  • Primarily multi-hop reasoning: Apache AGE covers moderate graphs; Chapter 14 covers dedicated graph memory.
  • Write-heavy streaming ingestion with no tuning or vacuum budget.
  • A single user with a few hundred notes: flat files (Chapter 01) or SQLite (Chapter 12) need less.
  • Teams unable to operate Postgres. Managed hosting handles provisioning, patching and most backups; tuning, vacuum, extension upgrades and RLS remain yours.

Use cases

Row counts here are assumed sizes.

1Shared documentation assistant

Situation
A team searches 8,000 documentation passages and needs exact error-code matches alongside paraphrases.
Why it fits
SQL combines keyword and vector ranks on the same rows,14 so no second store needs synchronising.
Pair with
Pre-release EXPLAIN and model revision metadata. Chapter 05 covers reranking.

2Per-user assistant memory in a SaaS app

Situation
A support assistant remembers preferences and tickets: 5,000 users, about 2,000 memories each, 10 million rows total.
Why it fits
RLS keeps each user's rows private.15 At 2,000 rows per user, exact user_id-indexed search gives perfect recall. Shared HNSW can underfill even with iterative scans (continuing until enough rows pass the filter); see Gotchas.1
Pair with
Use the partial user index; partition and vector-index large tenants only when filtered exact search misses budget.1 Compare Chapter 11 if tuning still misses latency.

3Booking agent with an audit trail

Situation
A booking agent records "prefers aisle seats" with 200,000 yearly reservations; compliance requires every change logged.
Why it fits
The memory, reservation, audit and outbox rows commit together, preserving the pending Redis cache refresh (Chapter 09).
Pair with
A worker retries pending outbox rows, so refreshes must be safe to repeat. NOTIFY only wakes the worker; a missed one does not lose the row.16 See Chapters 09 and 17.

4Support agent that must match order numbers

Situation
An agent searches 300,000 past tickets. Embeddings blur an error code or order number, and a pure keyword search misses paraphrases.
Why it fits
tsvector with GIN and an HNSW index sit on the same rows, and RRF merges their rankings in one statement.14
Pair with
ParadeDB BM25 if keyword ranking quality matters more than ts_rank_cd.12

5Facts that change over time

Situation
A sales assistant tracks 100,000 customer facts. "Works at Acme" must become "worked at Acme" when the customer moves, without losing history.
Why it fits
A valid_to column marks superseded rows: one transaction closes the old fact and inserts its replacement and audit row. A partial index on null rows keeps current-fact lookups small.
Pair with
A fact-extraction model (Chapter 06). Chapter 14 covers temporal graphs when relations outweigh rows.

Numbers

Result quality. Filtered HNSW can finish quickly yet underfill (see Gotchas).1 Measure count, recall and p95/p99 under expected concurrency. Run pgbench -c CLIENTS -T 60 -l -f read.sql; compute logged transaction-latency percentiles against an exact-search baseline. Exact cost follows eligible rows per user; no universal cutoff applies.

Storage. The documented 4d + 8 bytes for vector(d) gives 1,544 bytes at 384 dimensions, confirmed here.1 Tested table storage was 163,905,536 bytes (156 MiB) for 100,000 rows. Vector-only extrapolations: 1.54 GB per million, 15.44 GB per ten million, excluding text, indexes and replicas; not loaded tests.

Calls and tokens. A raw episode write needs no model call. An extracted memory costs one extraction call (Chapter 06) plus one embedding call. A semantic read costs one query embedding, and ten illustrative 100-token facts add about 1,000 prompt tokens plus wrappers. Keyword-only reads need no embedding call.

Time. Extraction and embedding calls add model time (Chapter 03) where used; the walkthrough timings report SQL time only. Chapter 20 measures caching of repeated finished answers.

Create and index the memory tables

setup.sql creates the episode and memory tables with a user-qualified foreign key, validity dates, embedding provenance and full-text data. It loads 20,000 seeded random vectors, shows plans before and after HNSW, keyword and current-user indexes; exact search suffices here. The fixture assigns users by i % 20 and text by (i / 20) % 4, so each user has all four texts. Fusion asserts keyword-only, vector-only and both-list hits. Bulk loading uses autocommit; the supersession step below demonstrates a transaction. Without i * 0, Postgres would evaluate the ARRAY subquery once, giving all 20,000 rows the same random vector.

Check search, isolation and supersession

recall.sql runs keyword, vector and fused search, compares approximate results with the exact top 10, and tries default, iterative and wider HNSW scans. Searches use stored vectors (id = 1 or 22) as queries, under the table owner before RLS. At LIMIT 50 the vector branch sorts the user-index rows exactly; at LIMIT 10 the planner chooses HNSW, exposing underfill and recovery with iterative or wider scans.1

With HNSW present, materialize filtered current rows in a CTE before sorting for exact search. Fusion needs unrounded RRF ordering, rounding only for display. The keyword parser ANDs terms: extract key terms or use OR; test code tokenization.

Supersession needs a lab repair: row 22 is a travel fact; use preference row 2 with a newly computed embedding. The copied vector is wrong; stale retries can duplicate outbox rows. Enqueue only this transaction's audit RETURNING rows; zero means stale. Validity boundaries match. NOTIFY has no listener here (Chapter 09).

RLS assertions then check unset-identity and Alice/Bob isolation, aborting on failure. Owners bypass RLS unless forced; use a non-owner without BYPASSRLS.15 Set app.user_id with set_config('app.user_id', $1, true) in the query's own transaction to expire at commit; session-level SET survives for the next pooled caller. Only trusted application code may hold this role, deriving identity from authentication; exclude caller- or agent-supplied SQL. After COMMIT, current_setting('app.user_id', true) returns an empty string, hence NULLIF. Both tables reject empty user_id; post-COMMIT isolation is asserted on the same connection.

CREATE TEMP TABLE fused AS
WITH q AS (SELECT embedding AS e FROM memories WHERE id = 1),
semantic AS (
  SELECT id, row_number() OVER (ORDER BY dist) AS rnk
  FROM (SELECT id, embedding <=> (SELECT e FROM q) AS dist FROM memories
        WHERE embedding_model = 'test-fixture-384'
  AND user_id = 'user2' AND valid_from <= now() AND valid_to IS NULL
        ORDER BY embedding <=> (SELECT e FROM q) LIMIT 50) s
),
keyword AS (
  SELECT id, row_number() OVER (ORDER BY score DESC, id) AS rnk
  FROM (SELECT id, ts_rank_cd(tsv, query) AS score
        FROM memories, plainto_tsquery('english', 'agent memory') query
        WHERE embedding_model = 'test-fixture-384'
  AND user_id = 'user2' AND valid_from <= now() AND valid_to IS NULL AND tsv @@ query
        ORDER BY score DESC, id LIMIT 50) k
)
SELECT m.id, m.content, s.rnk AS vector_rank, k.rnk AS keyword_rank,
       round((coalesce(1.0 / (60 + s.rnk), 0)
            + coalesce(1.0 / (60 + k.rnk), 0))::numeric, 5) AS rrf
FROM semantic s
FULL OUTER JOIN keyword k ON k.id = s.id
JOIN memories m ON m.id = coalesce(s.id, k.id)
ORDER BY rrf DESC, m.id;
SELECT id, content, rrf FROM fused ORDER BY rrf DESC, id LIMIT 3;
SELECT count(*) FILTER (WHERE vector_rank IS NULL) AS keyword_only,
       count(*) FILTER (WHERE keyword_rank IS NULL) AS vector_only,
       count(*) FILTER (WHERE vector_rank IS NOT NULL
                         AND keyword_rank IS NOT NULL) AS both_lists FROM fused;

Gotchas

Gotcha: exact search slows down silently

A bare vector column returns correct answers at any size, only more slowly. Check EXPLAIN before launch and during growth: sorting a whole-table sequential scan may be unintended, while sorting user-index rows is intended exact search. Alert on p99 and rows sorted, not plan shape alone. Chapter 19 reports audit-discovered unindexed search; its fix remains unconfirmed.19

Gotcha: filters shorten the result

HNSW finds distance candidates before the WHERE filter, so it can underfill LIMIT even for thousands of eligible rows (a 5% filter keeps about 2 of 40 candidates). Tested at ef_search 40 and LIMIT 10 on the 100,000-row table, one-user filters averaged 2.025 rows with 20 equal users (5,000 rows each) and 0.005 rows with 5,000 users (20 rows each; 200 queries). Iterative scans raised the mean from 2.025 to 10.000 rows at 5% selectivity but only to 4.015 at 0.02% selectivity (eligible share), where the scan stopped at hnsw.max_scan_tuples (default 20,000). The 10-million-row case was not run. Counts do not measure eligible-top-10 recall. Consider higher ef_search, exact search over a selective user index, partial indexes or partitions.1

Gotcha: incompatible embedding spaces break search

Store immutable model-and-revision IDs in embedding_model and filter the vector branch on them; the fixture names a synthetic space. Re-embed and rebuild the indexes when the model, revision or dimension count changes (Chapter 03), validating the new space before switching reads; a dimension change also needs a second column or shadow table.

Gotcha: churn and old versions

For update-heavy memory, run current pgvector. After bulk updates or re-embedding, watch n_dead_tup and last_autovacuum in pg_stat_user_tables and the size of memories indexes; the README speeds HNSW vacuum with REINDEX INDEX CONCURRENTLY first.1 The changelog lists HNSW vacuum and index-repair fixes in 0.8.3 and 0.8.4.6

Security: IVFFlat index builds

CVE-2026-103484 affects pgvector versions before 0.8.7. A database user permitted to create an IVFFlat index can write data out of bounds during the index build, which could lead to arbitrary code execution. It concerns IVFFlat builds, not ordinary nearest-neighbour queries.20

Upgrade older installations to 0.8.7 or later before allowing IVFFlat index builds; the setup above pins 0.8.7. Its release tag is the version-bump commit of 2026-10-01; the announcement is dated 2026-10-05.6,21,22 Restricting who can create indexes reduces exposure during the upgrade but does not patch the extension.

Verdict

Verdict: the default store once memory is shared

Pick it when Postgres is installed, writes need transactions, users need database isolation, or queries mix filters, keywords and vectors. Start with exact search and add HNSW when it exceeds a p99 SQL budget from your end-to-end latency target, at expected concurrency. Keep per-user search exact as described above; reserve HNSW for shared or large-tenant corpora with iterative scans, partial indexes or partitions.

Reconsider it when latency still misses the target after tuning, or when multi-hop relationships are the core need. Try pgvectorscale (label-filtered or disk-resident search) or VectorChord (quantized IVF with reranking) on dedicated hardware first, then a dedicated vector store (Chapter 11) or graph memory (Chapter 14). Chapter 22 (case study) shows row-level security as a second boundary below a patient-scoped gateway. Chapter 20 combines exact vector search, dated facts and a response cache in a single-user assistant.
