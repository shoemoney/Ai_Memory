What it is

An LLM-maintained wiki is a git repository of Markdown pages an agent maintains from sources. A person reads and reviews it.

Andrej Karpathy described the pattern in a gist titled "LLM Wiki", created on 4 April 2026. It is an "idea file" for an agent such as Claude Code or Codex.1 It contains no code.1

Chapter 01's flat files hold notes. A wiki maintains source-derived claims with cross-references and contradictions. Retrieval over raw chunks (Chapters 03 and 05) rebuilds those links for every question. Two families follow: agent-written Markdown wikis and context databases (OpenViking), which retain files and summarize directories.

Terms new in this chapter

Schema
A file such as AGENTS.md or CLAUDE.md specifying page format and ingest, query and lint steps.
Ingest, query, lint
The three loops: add a source, ask a question, check the wiki's health. Lint is a structural script on every commit plus periodic agent semantic lint.
L0, L1, L2
Three detail levels in a context database: a short abstract (about 256 characters by default), a longer overview (about 4,000 characters), and the original files.

BM25 (keyword ranking), embeddings, vector search and reranking are defined in Chapter 00 and the glossary.

How it works

The gist defines immutable raw sources, an LLM-written wiki (summaries, entity and concept pages, cross-references, overview), and a schema specifying page structure and workflows, its key configuration file.1

Two files anchor three loops. index.md is the catalog the agent reads first, one line per page; log.md is append-only, with a prefix grep can find, such as ## [2026-04-02] ingest | Title.1 During ingest, the agent reads a source, summarizes it, updates the index and related pages; the gist says one source may touch 10 to 15 pages.1 In query, the agent follows index entries to pages and answers with citations. A query writes nothing; keeping an answer counts as ingest, with branching, lint and review. In lint, checks look for contradictions, stale claims, orphans and missing cross-references. The walkthrough tests structural lint; semantic lint is specified but untested.1

Searching a wiki

The gist reports an index serving about 100 sources and hundreds of pages without embeddings.1 Beyond that, add search in this order:

  1. Keep index.md while it finds the right pages on recurring test questions; add search if it recovers missed pages at acceptable cost.
  2. Add rg (ripgrep, exact text) or qmd search (BM25 keyword ranking, no model; qmd is a local search tool) when you know the words.
  3. Add qmd query when you do not: it combines BM25, vector search and LLM reranking, all on your machine, and qmd has a CLI and an MCP (Model Context Protocol) server.2

A vector index over both raw/ and wiki/ can rank generated pages above human-written sources (embedding retrievers show this bias; see Numbers), so check that raw quotes still surface.

The second family: context databases

A context database retains files and adds two model-written directory summaries. OpenViking, an open-source project from Volcengine, presents knowledge, memory and skills as one virtual filesystem under viking://, with ls, read and grep to scan summaries before files.3

L0 lives in a hidden .abstract.md file, L1 in .overview.md, and L2 is the original file, read only when needed. Imported files get wrapper directories and thus directory summaries (Walkthrough, step 8).4 The server needs an embedding model and a summary model, from providers such as Ollama. The summary model uses the vlm (vision-language model) key even when it is text-only.5 The ov client offers ov read for files or summary URIs, ov find for embedded-query vector search over a target directory’s L0/L1/L2 records with optional reranking, and ov search for LLM query planning from session context.6

Good for and not for

Good for

  • One person or small team researching one domain over weeks, such as due diligence.1
  • A few hundred pages or fewer, with reliable index navigation.1
  • Work where every change should be reviewable in git.1
  • A large project directory that needs summaries without hand-written pages (use a context database such as OpenViking).

Not for

  • Large or fast-changing data such as tickets or logs: use retrieval over the raw data (Chapters 03 and 05).
  • Company-wide knowledge with one curator. A vendor argues the pattern does not scale to a company.11
  • Exact recall of original text. A wiki is synthesis, so keep and cite the raw sources.
  • Many writers and no human review. Use a database with access controls (Chapter 08).

Use cases

1One analyst, one research file or decision log

Situation
An investor reads 60 filings, papers and articles on one company over two months, asking what each claims and where they disagree.
Why it fits
Each document is ingested once, within the gist's scale.1 Semantic lint is untested here; its conflict-detection rate is unknown. The schema requires source tags, which structural lint can check.
Pair with
Obsidian as the viewer, raw PDFs in raw/ for exact quotes, and a person reading every diff.

2Several agents on one shared wiki

Situation
Coding and research agents overwrite each other's wording in one knowledge base; their flat memory files scatter and duplicate facts.
Why it fits
Schema and lint give agents shared rules; flat files become an immutable compilation inbox. One home-lab wiki works this way, but its backlog was about four fifths uncompiled (Numbers). It fits only while review keeps pace: cap agents or sources to what the merger can review.
Pair with
Per-agent branches, pre-commit lint, backlog counts and a human merger. Every ingest appends to index.md and log.md, so the second of two parallel branches conflicts there: rebase each branch on main first.

3A large project directory for a coding agent

Situation
A team keeps a few thousand files of API docs, design notes and runbooks. Grep finds the words but not the directory, and nobody will hand-write a wiki of it all.
Why it fits
A context database summarizes each directory at import, so the agent reads an L0 or L1 to pick a subtree, scopes find to it and reads L2 for the hit.3,6
Pair with
A capable summary model, a test that re-import skips unchanged files, and a review of the summaries (see Gotchas).

    The schema puts hard rules first.1

    markdownAGENTS.mdTested
    # Wiki schema
- raw/ holds sources. Never edit or delete a file there.
- wiki/ holds the agent's pages. One fact lives on one page.
- Start pages with YAML metadata between two --- lines (frontmatter):
  title, type, updated (YYYY-MM-DD), sources (YAML list of raw/ paths).
- Tag every claim [src:raw/<file>] or [UNVERIFIED]. Link with [[slug]].
- Every page needs an inbound link from another page; index.md does not count.
- Ingest: read the new raw file, write or update pages, update wiki/index.md,
  append one line to wiki/log.md, run bin/wiki-lint, commit on a branch.
- Index line: - [[slug]] - one sentence. Log line: ## [YYYY-MM-DD] op | title
  (op uses lowercase letters or hyphens, e.g. ingest or semantic-lint).
- Query: read wiki/index.md first, open the pages it points to, cite page
  names. For an exact quote, open and cite its tagged raw source.
- Lint: run bin/wiki-lint. Fix every ERROR before committing.
- Semantic lint, every 10 ingests or weekly: on a branch, report where changed
  pages contradict or outlive their raw sources (page, claim, source A,
  source B, verdict). Keep both attributed values (Acme 40% [src:raw/acme.md];
  Beta 35% [src:raw/beta.md]) unless a later source retracts the earlier one.

  2. Write the lint script and the commit hook, then commit the skeleton on main

    Structural lint validates frontmatter, index entries, inbound links, source tags/files, targets and log format; failures exit 1, stopping commits. Stage everything: checks read disk, not the staged snapshot. Python checks delimiters, PyYAML 6.0.3 frontmatter, four keys and ISO dates.16,17 Tags do not prove every claim is tagged or true. Check at least three changed source-tagged claims against raw text, or all if fewer changed; keep unsupported claims [UNVERIFIED]. Ingest corrections as new attributed sources: staged changes to existing raw files are refused.

    bashbin/wiki-lintTested
    #!/usr/bin/env bash
cd "$(dirname "$0")/.." || exit 2
err=0
fail() { echo "ERROR $1"; err=1; }
changed=$(git diff --cached --no-renames --name-only --diff-filter=CDMRTUXB -- raw/)
[ -z "$changed" ] || fail "raw/: existing sources are immutable"
for f in wiki/*.md; do
  s=$(basename "$f" .md)
  case $s in index|log) continue ;; esac
  if ! python3 - "$f" <<'PYAML'
import datetime, pathlib, re, sys, yaml
path = pathlib.Path(sys.argv[1])
lines = path.read_text().splitlines()
try:
    if not lines or lines[0] != "---":
        raise ValueError("no opening YAML delimiter")
    if "---" not in lines[1:]:
        raise ValueError("no closing YAML delimiter")
    end = lines.index("---", 1)
    data = yaml.safe_load("\n".join(lines[1:end]))
    if not isinstance(data, dict):
        raise ValueError("frontmatter must be a mapping")
    missing = sorted({"title", "type", "updated", "sources"} - data.keys())
    if missing:
        raise ValueError("missing keys: " + ", ".join(missing))
    if any(not isinstance(data[k], str) or not data[k].strip()
           for k in ("title", "type")):
        raise ValueError("title and type must be nonempty strings")
    if not isinstance(data["sources"], list) or not data["sources"] or any(
        not isinstance(v, str) or not v.strip() for v in data["sources"]
    ):
        raise ValueError("sources must be a nonempty list of paths")
    raw = pathlib.Path("raw").resolve()
    for source in data["sources"]:
        target = pathlib.Path(source)
        if not source.startswith("raw/") or not target.is_file() or not (
            target.resolve().is_relative_to(raw)
        ):
            raise ValueError(f"invalid source {source}")
    for source in re.findall(r"\[src:([^]]+)\]", "\n".join(lines[end + 1:])):
        if source not in data["sources"]:
            raise ValueError(f"unlisted source tag {source}")
    date = str(data["updated"])
    if not re.fullmatch(r"[0-9]{4}-[0-9]{2}-[0-9]{2}", date):
        raise ValueError("updated must be an ISO date")
    datetime.date.fromisoformat(date)
except (ValueError, yaml.YAMLError) as exc:
    print(f"ERROR {path.stem}: {exc}")
    sys.exit(1)
PYAML
  then err=1; fi
  grep -q "\[\[$s\]\]" wiki/index.md || fail "$s: missing from index.md"
  others=$(ls wiki/*.md | grep -v -e "/$s.md$" -e "/index.md$" -e "/log.md$")
  grep -lq "\[\[$s\]\]" /dev/null $others 2>/dev/null || fail "$s: orphan, no inlink"
  grep -Eq '\[src:[^]]+\]|\[UNVERIFIED\]' "$f" || fail "$s: no [src:] or [UNVERIFIED] tag"
  for l in $(grep -o '\[\[[^]]*\]\]' "$f" | tr -d '[]' | sort -u); do
    [ -f "wiki/$l.md" ] || fail "$s: broken link [[$l]]"
  done
done
bad=$(grep -v -e '^$' -e '^# ' wiki/log.md |
  grep -Ev '^## \[[0-9]{4}-[0-9]{2}-[0-9]{2}\] [a-z-]+ \| ')
[ -z "$bad" ] || fail "log.md: line not in '## [date] op | title' form"
exit $err

  4. Search: ripgrep, then qmd installed inside the lab

    npm install --prefix puts qmd under the lab; the PATH line affects only this shell. qmd search is BM25 only, with no model. qmd embed and qmd query download three GGUF models into the lab's cache: an embedding model, a reranker and a query-expansion model. Embedding the four files took 33 seconds on CPU; the first query spent 61.7 seconds on query expansion, then ranked index.md first (it mentions every page; four tiny files cannot show whether qmd helps).2 Each qmd command saves full output before grep selects display lines. Empty grep results are tolerated; failed qmd commands stop the lab. The last check verifies the cache under $XDG_CACHE_HOME/qmd.

Gotchas

Gotcha: repeated rewrites corrupt documents

DELEGATE-52 found agentic tool use did not reduce long-workflow editing corruption; larger documents, longer interactions and distractor files worsened it.12 Repeated wiki rewrites resemble that workload (inference; wikis were not tested). Review every agent rewrite. Structural lint catches missing index lines and broken links, not dropped caveats. Keep raw sources immutable and review diffs against them, applying step 2’s changed-claim checks and [UNVERIFIED] rule. Human review is the tested control; semantic-lint detection is unmeasured.

Gotcha: the compile backlog

Maintenance shifts effort from notes to schema and lint.1 Count un-ingested sources and unreviewed ingest branches. If either grows, stop sources or narrow scope until ingest and review catch up.

Gotcha: generated summaries can be wrong

The 1.7B abstract omitted feedback.md despite full sampling (step 8). The decisions overview invented Postgres reasons ("performance, scalability, and the existing infrastructure") and an invalid link, viking://input_sample_f1, rejected by the server. The file gives SKIP LOCKED, team size, volume and a revisit threshold, not those invented reasons. Summaries varied; retrieval found the files. Use a stronger summary model (Chapter 06); abstracts are pointers. Spot-check L0/L1 for three known files: passing summaries invent no facts or links.4

Gotcha: summaries can be sampled and pending

OpenViking’s default sample covers 32 direct children (semantic.overview_sample_limit).4 Above that limit, parent overviews lag until pending changes reach 10% of entries (semantic.freshness_refresh_ratio); no timed refresh is promised.4 Read raw .overview.md (step 8); ov abstract and search previews hide metadata. Positive pending_child_changes means lag; positive unsampled_entries means skipped children, requiring direct reads. The three-file lab cannot test sampling.

Unverified: open questions

  • Where cross-linking pays. A vendor says 100 to 200 notes, as "community calibration"; the post gives no measurement.18
  • Whether the OpenViking gains on LoCoMo (a long-conversation memory benchmark, see the glossary) hold outside the maintainers' evaluation. They report 80 to 83% for three agents versus 24 to 57% on built-in memory, using Volcengine’s Doubao models. Not reproduced here; the local test used a 1.7B model.3
  • The obsidian-llm-wiki retrieval claim. Its README compares Personalized PageRank with nearest-neighbor retrieval on a private vault, not a public benchmark. Its scoring denominator is unspecified.9

Verdict

Verdict: a good second step after flat files

Pick a wiki when one person or small team maintains a few hundred pages of lasting domain knowledge with diff review and lint. Linked, dated, source-cited pages remain readable and revertible without retrieval infrastructure.1 Evaluate a context database when index navigation fails recurring questions and you can run a server. Untested large-directory overviews require checks at every level. The tested 1.7B model failed (Gotchas). Before adopting, check a stronger model (Chapter 06) and time unchanged/edited re-imports on your corpus.

Add qmd when the index misses pages on recurring test questions, retrieval over the raw data (Chapters 03 and 05) when the data is large or changes fast, and a database with access controls (Chapter 08) when many writers need isolation. Skip the wiki if you cannot keep up the lint and review loop.
