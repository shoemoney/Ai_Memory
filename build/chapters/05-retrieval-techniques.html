Retrieval techniques

Retrieval turns a question into a short ranked list of stored notes: scope, search two ways, merge, rerank, then measure.

Maturity

Anyone whose memory store is too big for the prompt.

What it is

Retrieval picks the few saved notes that fit an assistant's prompt from thousands stored.

Each search returns n; merging yields N distinct candidates; a reranker orders them and the top k enter the prompt. Anthropic uses N=150 and k=20.1 Set k from the context budget; those figures illustrate one operating point.

Terms new in this chapter

Candidate pool
Distinct first-stage results; N cannot exceed summed search limits: 2n for two searches of n each.
Reranker (cross-encoder)
Scores question and chunk jointly, per pair at query time, unlike stored-vector comparison. Apply it only to the pool; sorting scores is reranking.
Recall@k
The share of known-correct notes in the top k results.
MRR
Mean reciprocal rank: average 1/rank of each question's first correct result; 0 for no hit within the evaluated list.
RRF
Reciprocal Rank Fusion. Merges lists by rank alone.
MMR
Maximal Marginal Relevance. Balances relevance against similarity to chosen results.
HyDE
Hypothetical Document Embeddings. An LLM drafts a plausible answer, which is embedded and searched instead of, or alongside, the question.
Average precision
Sum precision at correct results' ranks, divide by the known-correct count, then average across questions for mean average precision (MAP). Early hits score higher.

BM25 (keyword ranking) is defined in Chapter 00/glossary. Agentic search is iterative, model-directed retrieval through tools.

How it works

Build the golden set

A golden set pairs questions with answering note IDs. Test exact IDs, semantic matching through paraphrases sharing no words, and multi-answer recall through two-note questions. Compare identical questions:

  • recall@k, measured on the pool as well as the final list. Pool recall is the share found among all candidates; it caps later stages and shows whether reranking can help.
  • MRR, which rewards putting one right answer first.
  • Mean average precision (MAP), used in Numbers, rewards finding several right answers early.

With 20 equally weighted questions, one moves mean recall by up to 0.05; smaller gaps need more examples.

Scope before the limit

Rule: scope every search before its limit. Apply trusted user/project checks and metadata/time filters inside each search, before external rerankers see text. Recency, importance and MMR rank results; they never replace access controls.4,5 If filtering leaves fewer than k candidates, log and return fewer. Widen only a documented freshness preference, never an explicit date range, retention rule or user or project scope. Chapter 22 shows this for one patient per search.

Ranking without mixing score scales

Keyword/vector scales differ; RRF merges by rank. SQLite FTS5 returns BM25 scores where smaller means more relevant, so an ascending ORDER BY bm25(fts) puts better matches first.6 PostgreSQL uses its own full-text ranks, not BM25.7 RRF discards score magnitudes, giving even a weak match full credit for its rank. It sums 1 / (60 + rank) across lists. Second in both scores 0.03226; first in only one scores 0.01639.8

Preserve the meaning of each chunk

Keep headings with sections, questions with replies and paths with functions. Contextual Retrieval prepends 50 to 100 LLM-written tokens to each chunk before embedding and keyword indexing.1 Late chunking embeds the whole document first, then pools token vectors into chunks.9

First-stage variants

Learned sparse retrieval, such as SPLADE, has a model output weighted vocabulary terms for an inverted index. Late interaction (also called multi-vector retrieval) keeps one vector per token and matches each query token to its best document token: ColBERTv2 is the reference model and PLAID its fast index. BGE-M3 produces dense, sparse and late-interaction outputs from one model.10,2,11,12

Rerankers

Raise n until pool recall levels off or reranking reaches budget. Each candidate costs one pair score; benchmark end-to-end p95 at realistic chunk lengths, batching and concurrency. Three options:

  • Qwen3-Reranker-0.6B: Apache-2.0, 0.6B parameters, 32K tokens, runs on your hardware.13
  • Jina reranker v3.5: CC-BY-NC-4.0 (non-commercial), 0.6B parameters, 131K tokens, runs on your hardware or Jina's API.14
  • Cohere Rerank 5: managed service when hosting is impractical; text leaves the machine. Its listed context window is 32,768 tokens.15

Agentic search and repository maps

For changing code, an agent can read the current checkout or query an existing index. Claude Code's creator reports better results than RAG on his own code (Chapter 01).16

A repository map supplies paths and symbol signatures before full-file reads. Aider's 22 October 2023 design uses tree-sitter definitions and references instead of ctags, ranking a file-dependency graph to fit signatures into a token budget.25 A language server can supply symbols, definitions, references and call hierarchies through the Language Server Protocol (LSP).26 (From docs, not run.) Prefer a map for whole-repo structure; add LSP for precise definitions or call hierarchies when a server is available.

Refresh symbols after edits; generated code and dynamic calls can leave gaps. Use grep for exact text and embeddings for paraphrases, then read current source before editing. Compare file recall and prompt tokens; no comparison was measured here.

Hierarchical summary-tree retrieval (RAPTOR)

RAPTOR builds a hierarchy of summaries at write time: it embeds leaf chunks, clusters related ones, has a language model summarize each cluster, embeds the summaries and repeats for higher levels.17 At query time the collapsed tree flattens all levels into one list, searching chunks and summaries together by similarity within a token budget. This costs one query embedding and no summary call.17 Writing costs one summarization call per cluster at every level plus one embedding per leaf and summary; corpus-dependent cluster counts make per-document cost variable.18

The checked implementation rebuilds on additions, with no incremental update or deletion route. Track dependencies: replacing leaves requires refreshing summaries and embeddings, possibly reclustering. Deleting only leaves retains their information in summaries; rebuild or invalidate before serving. The implementation stores child-node IDs; add source document, version and page or chunk IDs and verify answers against the leaves, since a summary is not a quotation.17,18 The paper reports gains over flat retrieval on long-document questions, including QASPER research papers, but no comparison with entity graphs (Chapter 14). Test it where flat top-k retrieval cannot synthesize across passages, and compare answer quality, source coverage and rebuild cost on your golden set. Late chunking keeps context without summary levels.17,9

Soft forgetting: lower retrieval strength without erasing

Unused memories can lose ranking weight while retaining evidence. The Generative Agents paper (April 2023, section 4.1) scores recency as recency = 0.995^h, where h is sandbox game hours since the memory was last retrieved, and retrieval refreshes that clock; the final score also combines normalized relevance and importance.4

The released code differs: the August 2023 repository snapshot computes recency_decay^i over positions i in a list sorted by last access, not over elapsed hours.19 A policy proposed here (not from the paper): refresh strength on verified use, not retrieval alone; pin confirmed enduring preferences; keep strength separate from authorization and retention, since hard expiry or required erasure must remove the memory from live reads whatever its score (Chapters 10 and 17). No gain was measured.

Good for and not for

Good for

  • A memory store too large to put in the prompt whole.
  • Mixed questions: exact IDs and codes next to paraphrases.
  • A store you can test with 20 real questions, keeping only the steps the numbers support.

Not for

  • If authorized notes fit the context and cost budget, compare loading that scoped set whole; Anthropic suggests caching below about 200,000 tokens. Reuse cached contents only while authorized and current.1
  • Source code that changes all day without index refreshes. Use current-file search or refresh the symbol map.
  • Fixing duplicates or contradictions, which needs write-time rules, not a better ranker. Supersede contradictory notes when writing them (Chapters 13 and 14).

Use cases

1Small personal corpus

Situation
One person keeps about 5,000 prose, ticket and config notes. Dense search misses ticket numbers; keyword search misses paraphrases.
Why it fits
BM25 catches exact tokens and a small embedding model catches paraphrases. RRF merges the lists with one constant and no score tuning.8
Pair with
Chapter 12 for the SQLite setup. Add a reranker only if the top five are noisy.

2Code in a repository

Situation
An agent works in a large, hourly-changing repository with exact function names, flags and paths.
Why it fits
Agentic search runs grep and glob on current files, seeing the current checkout.16 Saved code notes need repository, path, symbol and commit metadata to flag or suppress stale notes; ClickHouse's Loom, an agent-memory product, documents one vendor implementation.20
Pair with
Chapter 01 for notes beside the code and its freshness policy for stale ones.

3Chat history

Situation
An assistant keeps months of chat and must answer "what did I say about the router last week" and "what was that error code".
Why it fits
Use indexed-field equality for exact codes, FTS5 for words/token phrases. Filter to the requested week before ranking; dense handles paraphrases and recency favors recent turns.4
Pair with
Index each complete turn with its preceding turn's ID. After retrieval, fetch the preceding turn for context and include each turn only once.

4Long documents

Situation
A team indexes 400-page manuals whose sections repeat headings like "Overview" and say "this setting" without naming it.
Why it fits
Anthropic reports Contextual Retrieval cut top-20 failures by 49%, and by 67% with reranking; Numbers checks the full pipeline locally; keyword search and reranking may explain its gain.1 For text that fits a long-context embedder's input window, late chunking is a cheaper route.9
Pair with
Hybrid search, then rerank the top 150 down to 20.1

5A corpus that changes daily

Situation
A support team edits notes daily. Old answers must not outrank today's; nightly re-embedding of everything is wasteful.
Why it fits
Keyword indexes update cheaply on write. Hash each chunk's embedding input, headings and prefixes included, and re-embed only changes, plus chunks whose prefix depends on a changed document. Mark replaced versions inactive on write and exclude them in both searches before the limit; use recency only to order eligible notes.
Pair with
Write-time supersede rules in Chapters 13 and 14. For files that change within a session, fall back to agentic search.

Cost and scale

  • Writes and reads: one embedding per chunk and query; keyword indexing and RRF need no model. Reranking scores at most 2n pairs for two first stages of n, even with batching.
  • Storage and scans: 384-dimension float32 vectors take 1,536 bytes each: 153.6 MB for 100,000 chunks or 1.536 GB for one million, before text and indexes (Chapter 00). Exact search scans every vector per query: ten concurrent uncached queries at one million rows read roughly 15.36 GB before reranking. Embedding and scoring add time; latency was not measured.
  • What to do: more users multiply rows and more agents multiply queries, so measure p95 retrieval time and pool recall under load. If scans exceed the latency budget, move to indexed pgvector (Chapter 08) or a dedicated store (Chapter 11). If concurrent writes stall, move to PostgreSQL (Chapter 08).

  4. Search, merge and rerank

    Save as search.py. Keyword search quotes tokens to avoid FTS syntax errors; it splits TS-999 into OR-ed TS and 999. BM25 ties break by rowid; dense has no secondary tie order. Fusion and reranking ties break by note ID. Each stage returns five candidates (n; sqlite-vec calls it k), giving up to ten pooled. In rrf, rrf_c=60 is the RRF constant. Smaller pinned TinyBERT keeps the fixture fast, scoring only that pool; it is not a recommendation.23

def bm25(q, n=5):
    words = re.findall(r'\w+', q)
    if not words:
        return []
    match = ' OR '.join('"%s"' % w for w in words)
    return ids(db.execute('SELECT rowid FROM fts WHERE fts MATCH ? '
                          'ORDER BY bm25(fts), rowid LIMIT ?', (match, n)))

def dense(q, n=5):
    v = struct.pack('<384f', *model.encode(q, normalize_embeddings=True))
    return ids(db.execute('SELECT rowid FROM vec '
                          'WHERE embedding MATCH ? AND k=? '
                          'ORDER BY distance', (v, n)))

def rrf(rankings, rrf_c=60):
    scores = {}
    for ranking in rankings:
        for rank, doc in enumerate(ranking, 1):
            scores[doc] = scores.get(doc, 0.0) + 1 / (rrf_c + rank)
    return sorted(scores, key=lambda d: (-scores[d], d))

def hybrid(q, n=5):
    return rrf([bm25(q, n), dense(q, n)])

def rerank(q, pool):
    if not pool:
        return []
    bodies = [db.execute('SELECT body FROM notes WHERE id=?', (d,)).fetchone()[0]
              for d in pool]
    scores = reranker.predict([(q, b) for b in bodies])
    return [d for _, d in sorted(zip(scores, pool), key=lambda x: (-x[0], x[1]))]

def hybrid_rerank(q, n=5):
    return rerank(q, hybrid(q, n))

Gotchas

Gotcha: a reranker cannot fix a pool miss

In the walkthrough the five-candidate BM25 pool misses n16, so reranking cannot recover n16. If pool recall is low, improve the first stage with a better chunk, a rewritten query or a second search.

Gotcha: FTS5 query syntax breaks on hyphens

Unquoted agent-memory in MATCH fails with "no such column: memory", because the unquoted hyphen is query syntax, not part of a literal phrase. A parameterized query does not help: the query language lives inside the parameter. Quoting each word, as the bm25 function in search.py does, avoids the error but splits the ID into OR-ed tokens. Quote the whole ID to require adjacent tokens in order. For literal identifier lookup, index the ID in a separate column and use equality.

Verdict

Verdict: build the golden set first

Write 20 real questions first. Then compare BM25, one dense model and their RRF merge on a store you already run. Test reranking when pool recall meets your target but recall@k or MRR@k lags at serving cutoff k. Set targets from missed-answer costs. With 20 questions, one or two misses signal only that the set must grow. If correct notes rarely enter the pool, fix retrieval first. Test heading-aware chunks or Contextual Retrieval for lost context. Failure was lower on these 150 LoCoMo questions and inconclusive on SciFact; keyword search and reranking may explain the gain.

Before shipping, freeze both pipelines and compare fresh labeled questions at the same context budget.
