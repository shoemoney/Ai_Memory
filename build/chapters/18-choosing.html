Choosing an architecture

Pick the smallest memory that fixes a failure you can see, then grow it by measured signals.

Compared

14 designs/components (Chapters 01 to 14), ten criteria; 3 further families, five criteria; 2 tools unrated.

Answered

12 head-to-head selection questions.

Routed

2 flowcharts from the kind of memory to a store.

Built

7 reference stacks, 4-step scale path, regional rule and nearest case study (Chapters 21 to 23).

The ratings are editorial judgments, not benchmarks. Start with “Start small” for capability gaps and the scale path for capacity limits; consult comparisons and stacks as needed.

Verdict: begin with files, and let evidence move you

Single-user tools and prototypes start with flat files and git history, then keyword search and embeddings in one SQLite file. Use Postgres for cross-host writes, tenant isolation or excessive contention. Trial a note-taking model when verified chat facts repeatedly go missing from notes; keep it only if omissions fall without more false writes. Use a task graph for blocked, claimed or ready work; notes suffice for simple hand-offs. Managed services trade operation for payment. If stable material fits the window, see “Long context or any memory”.

Decision flowcharts

Head-to-head answers

Flat files or an LLM wiki

  • Pick files when facts are short, stable and person-written. Keep them within the Chapter 01 limits.1
  • Pick a wiki when one agent maintains a few hundred pages on one topic, with diff review. Long rewrites corrupted 25% of content on average with three frontier models; this book's 7B run lost 71% in four edits.2,3
  • Combine: store notes in the wiki; point a short file to its index. Retain raw sources.

Keyword search or embeddings

  • Pick keyword search when question and note share words: identifiers, error codes, names. Anthropic illustrates an embedding miss with error code TS-999, found by keyword ranking;4 Chapter 05's 24-note embedder test found it. Test your corpus.
  • Pick embeddings when labeled questions miss relevant notes because wording differs. For a pile too large to scan, try indexed keyword search first.4
  • Combine: index text with FTS5 and sqlite-vec in one SQLite database; fuse rankings (tested with sqlite-vec 0.1.9 on SQLite 3.51.3).9

Text or multimodal embeddings

  • Pick text when the corpus is text. Qwen reports its 8B vision embedder averaging 67.88 on text, versus 70.58 for its 8B text model (not run here).5
  • Pick multimodal when you search screenshots, slides or photos directly. ViDoRe V3 reports visual retrievers beat textual ones on document pages.19
  • Combine: for a readable trail, embed image captions beside image vectors.

An embedding model or a note-taking model

  • Different jobs. Embedders index unchanged chunks by meaning; note-taking models extract facts from raw chat. Search unchanged chat when passages suffice.
  • Pick the note-taking model when you need discrete facts and the baseline repeatedly misses them. Each write calls a model; false facts stick. In Chapter 06's CPU test, thinking mode raised one schema-checked extraction from 3.4 s to 96.9 s. Queue the write, turn thinking off and review it. Use a stock model unless it fails: Chapter 07's ten-prompt test retained every fact with a stock small model; an uncensored model reversed one correction.
  • Combine: put a note-taking model before an embedder for semantic fact lookup. Mem0 packages this (see "A framework or building it yourself").

Redis, Memcached or Postgres

  • Pick Redis (or Valkey) when the data is the working layer (sessions, semantic cache, expiring keys, streams). It must fit RAM; crashes can lose the last second (AOF fsync every second, more with snapshots).7
  • Pick Memcached when you need a shared, disposable exact-key cache.
  • Pick Postgres when the record must commit with business data and row security separates tenants.6
  • Combine: Postgres with Redis as a hot tier that rebuilds from it, or with Memcached as a versioned answer cache (Chapter 20).

An embedded file, pgvector or a dedicated vector store

  • Pick one SQLite file when writes stay on one host, contention meets your latency budget, and you want keywords and vectors without a server (Chapter 12).9
  • Pick Postgres + pgvector when you run Postgres and want joins, transactions and row security. pgvector defaults to exact nearest-neighbor search. Measure approximate versus exact results (index recall), then labeled fact retrieval (retrieval recall). The pgvector README gives no approximate-index row cutoff.6
  • Pick a dedicated vector store or managed service when a tuned index cannot meet recall at the required p95 latency (step 4 of the scale path below), or you search page images with several vectors per page (late interaction, Chapter 11).
  • Combine: Postgres holds truth; rebuild the vector copy, recording each vector's model name/revision.

A framework or building it yourself

  • Pick a framework when you want extraction and search in few calls. Mem0 runs with Ollama and Qdrant.20 It needs a separate keyword branch when exact identifiers matter (Chapter 13).
  • Build it yourself when the schema is narrow, memory sits in your database, or you must audit writes. A plain retrieval baseline matched Mem0 at 8.4 times lower cost in one published comparison;10 this book's local run found about 16 times lower generation-token cost (Chapter 17).
  • Combine: a framework extracts and your store keeps the result. LangGraph has Postgres storage.21
  • Tested routes (Chapter 13): Hindsight, a self-hosted memory server, retained/recalled across restart; Letta Code passed scripted retention of explicitly saved information. Neither proves unprompted fact selection or minimum model/GPU requirements; measure yours.
  • For the surveyed tools in Matrix 3, preserve source exports and verify deletion from source and derived stores.17,18

Self-run memory or a managed cloud service

  • Pick a managed service when you prefer per-use billing to operating extraction/storage and can enforce user scopes. Prices checked 2026-11-20; recheck: Google Memory Bank bills $0.30 per GiB-month plus model tokens. AWS AgentCore bills $0.75 per 1K records-month and $0.50 per 1K reads, so 100,000 records and 1M monthly reads cost about $575 ($75 storage plus $500 reads); at an assumed 2 KiB per record, Google storage alone is about 0.19 GiB, or $0.06 monthly. These subtotals are not comparable: price identical saves, reads and model-token volumes.22,23 Microsoft Foundry Agent Service Memory, public preview, has quotas, no virtual network integration and changing model-usage bills (Chapter 13).30 AWS raw events expire within 365 days; delete derived records separately.24
  • Pick self-run when memory must stay on your hardware or every record must be inspectable.
  • Combine: the service extracts/serves memories; export source conversations separately, since derived records are not backups (Chapter 13).

Vectors or a knowledge graph

  • Pick vectors when questions are local lookups and facts are short. An independent LoCoMo long-conversation test scored Mem0/retrieval/full context at 77 to 81% answer accuracy, Graphiti/Cognee at 55 to 56% (Chapter 17 reruns locally with different settings).10
  • Pick a graph when facts have dates and links. Graphiti invalidates a replaced fact instead of deleting it,11 and keeps two timelines (Chapter 14).
  • Check the note-taking model: use a model that returns valid JSON (7B and 0.6B passed ingestion/search smoke tests; an earlier 0.6B trial timed out); Chapter 14 has the gotchas and the acceptance test.11
  • Combine: lookups and dated links: vectors as the base, the graph on top.

A task graph or notes

  • Pick a task graph when sessions or agents must track blocked, claimed or ready work. Beads bd ready lists unblocked items; claims are atomic within one database. Across replicas, route claims through one writer (stack 7).12
  • Pick notes when the content is facts and conventions that stay true. An issue tracker suffices with ready-work selection and atomic claims (Chapter 01).
  • Combine: Beads holds the plan and notes hold the conventions. A framework checkpoint (such as LangGraph's) resumes one run, replacing neither; rewind does not undo cross-thread store writes (see Chapter 13, Forked planning).

A context database, a wiki, a summary tree or plain search

  • Pick a context database when a folder has thousands of files and grep finds words but not the right directory. OpenViking generates per-directory L0 abstracts/L1 overviews for scoped vector search.13,14
  • Pick a wiki when one person reviews every page, or plain search (SQLite FTS5 or the qmd markdown search tool) for ranked passages only (Chapter 02).
  • Pick a summary tree when questions span themes across manuals/research corpora rather than passages or dated links. RAPTOR clusters chunks and summarizes them upward, at extra model calls per write (Chapter 05).25
  • Combine: the files stay your own and the database is a rebuildable index. Treat an abstract as a pointer: it is generated text.

Long context or any memory

  • Pick long context when stable material is small. Anthropic advises it under about 200K tokens with caching.4 Long-context GPT-5-mini beat a Mem0-style system on accuracy in one study.26
  • Pick memory when history outgrows the window. The same study found memory cheaper after about ten turns at 100K context;26 on this book's shorter local histories the break-even was about 49 questions, not turns (Chapter 17). Chapter 20 measures each addition's prompt tokens and correctness on 24 fixed questions.
  • Combine: memory picks what enters the window.

Seven reference stacks

Stacks are untested exactly as listed; Chapters 20 to 23 are nearest. Chapter 20 stages a community Qwen3.8-2B, Q4_K_M assistant. Build dependencies first; review writes. CPU-only runs from November 2026 (Chapters 05, 06, 07, 12, 14 and 20) show functionality, not retrieval quality at scale.

1Solo developer's coding agent

Situation
One developer, one or two repositories, Claude Code or Cursor; commands, naming rules and decisions disappear between sessions.
Why it fits
Files load without retrieval, grep finds the rest, and git reviews changes.1,27 Keep them short.
Build order
  1. Chapter 01: CLAUDE.md under 200 lines, scoped rules and notes with a dated index. Check past-decision answers in a fresh session.
  2. Chapters 02 and 17: dated decision notes, pruned monthly.
  3. Chapters 05 and 12: SQLite FTS5 only if grep stops finding things.

2Private assistant, fully local

Situation
One person, one small machine, nothing leaving it; Chapter 21 is closest, with different hardware and model size.
Why it fits
One SQLite file holds text, keywords and vectors. Pin pre-v1 sqlite-vec; use SQLite 3.51.3 or later (Chapter 12).9 Tests used Ubuntu CPU, and Chapter 21 a Mac mini; re-measure.
Build order
  1. Chapters 12 and 01: a short profile file and JSONL message log: one object per event with id, timestamp, role and text; a delete event names its target id so rebuilds omit deleted messages.
  2. Chapters 03, 05 and 12: FTS5 first; add Qwen3-Embedding-0.6B and sqlite-vec in that file after a paraphrase miss.
  3. Chapter 06: a note-taking model after each session, writes reviewed (Chapter 21 uses 9B versus Chapter 06’s 2B test), or Chapter 13 (Hindsight, tested locally).

3Social-media reply agent in its owner's voice

Situation
Drafts use the owner’s published voice and account context. A person approves every post.
Why it fits
Embed the fixed archive with each post’s URL and date. A note-taking model tracks changing, dated, sourced facts by account and marks superseded notes. Voice rules fit a flat file. Untrusted replies can poison memory: MINJA plants false memories through ordinary-looking queries (Chapter 17),28 so approval gates both publishing and writing.
Build order
  1. Chapters 01, 03 and 12: a voice file, and the archive embedded in one SQLite file with sources shown beside each draft.
  2. Chapter 06: one approved row per fact: note_id, account_id, fact, date, source_exchange_id, supersedes_note_id. Exclude superseded rows from current replies; keep extraction only if omissions fall without more false writes.
  3. Chapter 17: approval queue, trust labels, and a test requiring drafts to cite real posts and exclude superseded facts.

4Customer-support bot with many tenants

Situation
Hundreds of customers need isolated, changing facts and answer-time audits. Chapter 22 (per-patient isolation, audit) is closest.
Why it fits
Postgres + pgvector commits facts, embeddings, tenant and audit rows together, with row security.6 Many vector stores rely on your tenant filter; bugs leak data;8 check for native namespaces or per-tenant collections (Chapter 11). Valid and recorded times (Chapter 14) show which fact applied; log the version IDs cited.
Build order
  1. Chapter 08: tenant_id with row security; append-only fact versions with valid_from, recorded_at and supersedes_id. For past answers, select versions recorded by that date, excluding those superseded within that set; log cited IDs.
  2. Chapters 05 and 08: per-tenant search. Filtering approximate-scan candidates can leave fewer than k matches despite enough tenant records. Iterative scans probe within configured limits; raise limits or use exact search if needed. Test per-tenant recall against exact search.6
  3. Chapter 17: an outbox (change events written in the same transaction as the data) with event ids, and a tombstone per delete, so replay never restores a deleted record; trust labels, write gating, a cross-tenant test in CI returning zero foreign rows.
  4. Chapters 09 and 10: Scope Redis sessions by tenant/user/purpose. Answer keys add query and fact-set revision; advance it transactionally with corrections/deletes. Test that the next identical query misses the old answer. A managed service (Chapter 13, not run) can replace the store, with scope checks still in your code.

5Companion or role-play app

Situation
Months of character conversations need plot continuity and user memory.
Why it fits
SillyTavern layers hand-written lorebooks, generated summaries and optional vector retrieval of past messages, matching this stack’s files, log and summaries. Summaries can lose details or hallucinate.29
Build order
  1. Chapter 01: character card and lorebook files.
  2. Chapters 12 and 06: a JSONL log with FTS5; a local note-taking model appends one dated summary per session (Chapter 02).
  3. Chapters 03 and 07: vectors as a supplement; an uncensored model only if the stock note-taking model refuses legitimate role-play and the replacement passes the Chapter 07 correction test.
  4. Chapter 17: sample summary claims against the log. Regenerate summaries unsupported by the log; if they still lose or invent fixed plot facts, discard them and rely on the log.

6Team of cooperating agents

Situation
Researcher, writer and reviewer agents share facts and must not overwrite one another.
Why it fits
Shared Postgres with a version-checked pointer prevents stale overwrites. Shared-file writes can lose data.27 The MCP reference memory server locks writes but rewrites its growing file (Chapter 13). Ordered writes alone permit stale overwrites. LangGraph namespaces separate private notes; shared facts need version checks.21 Graphiti shares dated facts but needs structured model output (Chapter 14).11
Build order
  1. Chapter 08: shared Postgres with source_agent, recorded_at and supersedes columns. Use compare-and-set: append a version linked to its predecessor. Transactionally advance the current pointer only if that predecessor remains current. Otherwise roll back, re-read and retry; queue contradictory claims for human review.
  2. Chapters 13 and 09: a namespace per agent, and Redis streams for hand-offs, never as the record.
  3. Chapter 01: a task graph (Beads), so two agents cannot take the same task. Use the Chapter 01 multi-writer mode or route claims through one process; embedded mode allows one writer per database.
  4. Chapter 17: gate poisoned writes; test that two edits from one predecessor yield one commit and one conflict.

7Coding agent that resumes work across machines

Situation
Machine or agent hand-offs need completed, blocked and next work.
Why it fits
A task graph keeps the plan outside any session. Beads lists unblocked work and syncs through the git remote with bd dolt push and pull.12 Push before leaving; pull on arrival. Concurrent workers route claims through one writer: local claims do not reserve tasks elsewhere. Embedded mode allows one writer per database (Chapter 01 ran this against a local remote).
Build order
  1. Chapter 01: CLAUDE.md and the notes folder, committed; Beads 1.3.4 on both machines, bd ready first each session.
  2. Chapters 12 and 17: for offline search, commit only history-safe Markdown/JSONL; rebuild SQLite per machine. Tombstones suppress replay, not old commits or clones. For erasure, keep sources out of Git and choose a store and replica-retention policy supporting it. For offline edits, deduplicate event ids; send edits and base versions to one authoritative writer. It versions writes, rejects stale edits and retains versioned tombstones (delete markers) until every replica acknowledges deletion. Re-creation needs a new record ID.
  3. Alternatively, Chapter 13: one shared Hindsight server (tested on one host only; cross-machine use is untested), a per-repository bank, writes reviewed.

Scale path and the closest case study

This path adds capacity for users, writers or regions; “Start small” adds capabilities. Enter step 1 for keyword search or embeddings. Signals come from Chapters 01 to 14’s Scope and scale blocks and the case studies.

Deployment changes and their triggers

StepTake this step whenRead
1. One writer host: SQLite with FTS5 and sqlite-vecOne writer host; exact-scan and append time fit your latency budget. No universal user cutoff.Chapters 12 and 21.
2. Shared writes/tenants: Postgres + pgvector; Redis hot readsTenants need row security, another host needs direct writes, or local contention, exact-scan or append time exceeds your latency budget. Add Redis when repeated recall, embedding or session reads dominate. Set p95 and minimum recall targets on your test set (Chapter 17). Stay on exact search until p95 misses; then use approximate index scans (iterative for filtered queries), and go to step 4 when a tuned index still misses either target.Chapters 08, 09 and 22. 3. Several workers and inference serversThe write queue grows older than your freshness budget, or a long image or document job blocks live replies. Dedicated vector store or managed serviceOn labeled queries a tuned index misses recall at the required latency while exact top-k over the same eligible rows finds the fact (if both miss, revisit chunking, embeddings or keyword search first), or measured I/O on the working set (sizing in Chapter 00) makes the tuned deployment miss its latency or cost budget.
