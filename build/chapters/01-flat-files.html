Flat-file Markdown memory

The agent's memory is a folder of plain text files that it reads at session start or opens when needed.

Maturity

Shipped

Setup effort

1 of 5

Running cost

Best for

One developer or a small team with short, stable facts worth a human reading.

What it is

Flat-file memory is a notes folder for an AI agent. A developer writes the build command and naming rules into a repository Markdown file, and the agent reads it instead of being told each session.

No database or embedding model is needed. Anthropic's memory tool documentation describes its storage as "a directory of memory files" that your application stores as it likes.1 Anyone can edit or delete a file; Letta, an agent framework, calls them "simple, universal primitives that both humans and agents can work with using familiar tools".2

Terms new in this chapter

Frontmatter
A block of settings between two --- lines at the top of a Markdown file.
Hook
A script the harness or git runs on an event such as session end or commit.
Worktree
A git feature that checks out a branch in its own folder, so agents can work in parallel.
Item (Beads)
One entry in the Beads task graph: title, status, owner and links to the items blocking it.
Dolt
A SQL database with git-style commits, branches and remotes.

System prompt and RAG are defined in the terms box of Chapter 00, and harness in its first paragraph.

How it works

Two loading models cover almost every tool. In the first, the harness loads the file at session start. Claude Code delivers CLAUDE.md as a user message after the system prompt, loading it "at the start of every conversation".3

In the second, the agent reads files when needed: only an index or file tree stays in view. Anthropic's memory tool works this way: "Claude automatically checks its memory directory before starting a task", then views files under /memories.1

Letta's Context Repositories combine both: the file tree is always in the system prompt, each file has a frontmatter description, and system/ files always load fully.2

Where flat files stop: task state for coding agents

Shared task state, notes about changing code and reusable procedures need extensions to plain notes.

A coding agent needs to know what is left, what blocks what and who has taken which item. A Markdown list can record owners and blockers; a task graph computes ready items and lets an agent claim one atomically. Beads calls itself memory for coding agents that "replaces messy markdown plans with a dependency-aware graph".8

Items occupy a Dolt database under .beads/, with hash-based ids like tasks-dvc (project prefix plus a short hash) that avoid merge collisions. A link says one item blocks another.8 Claims assign work atomically; expired leases need explicit reclaim. Part 3 shows how another session or machine continues the plan.

A framework checkpoint (LangGraph, Chapter 13) saves a run for resumption.16 Beads keeps the plan outside runs for continuation by any agent, anywhere.

Code-linked freshness: notes about code that notice the code changed

“send() never retries” becomes wrong when retries are added, yet the model trusts it. Record the file, symbol and commit supporting each fact; check before use. GitHub Copilot Memory cites code locations for each fact and checks them against the current branch before use; GitHub reports no significant added latency in testing; its docs warn the check can err.15,17 Loom (vendor claim, not checked), an Apache-2.0 ClickHouse tool announced on 13 November 2026, follows a renamed function, flags a note when the function is rewritten, and never rewrites a note itself.18

MEX's README says its code checks cannot tell whether a note still means the right thing; meaning-based checks are future work.10

In plain files, put three frontmatter fields: file and commit are required, and symbol helps whoever reviews a flag. Part 1 step 3 flags notes whose cited file changed since the recorded commit (committed, staged or unstaged),19 or when the file or the commit is missing. Unlike MEX, it only reports. It skips notes without code-link fields, such as repository conventions; review those on a schedule. A rename shows as stale, and any edit to a cited file triggers review. For a valid code link, silence means git found no difference in the index or working tree. It does not validate the fact: retry behavior might have moved into a dependency. Before trusting a flagged note, test the cited behavior and inspect its dependencies; update the fields or delete the note.

Skills: who writes the procedure

A skill is a Markdown file of instructions. Only its description stays in context and the body loads when the skill is invoked, so write the description as a trigger; long procedures cost little until used.20

Human-writtenA person writes SKILL.md in Claude Code.20The author, in version control.

Automatic reuse is the riskiest row: a bad or poisoned procedure is reused unseen (Chapter 17). Default to human-written skills in version control; allow agent-written ones only behind a review or test gate.

Good for and not for

Why teams start with flat files

  • Grep is a real retriever. The Pragmatic Engineer's write-up of an interview with Boris Cherny, who created Claude Code, reports that local vector databases and recursive model-based indexing lost to model-driven glob and grep.22 A newsletter anecdote, not a benchmark.
  • Git history comes free. Letta's repositories "are git-backed, so every change to memory is automatically versioned".2

Good for

  • One developer or one small team, working in one repository or with one agent.
  • Short, stable facts people will read: build commands, conventions, preferences.
  • Portability: AGENTS.md is read by several tools, and Markdown notes move between tools with little rework.
  • A few thousand lines across on-demand notes (a rule of thumb, not measured; the lab chooses a separate 200-note threshold); always-loaded files near 200 lines; the MEMORY.md index within its 200-line, 25KB cap.

Not for

  • Many users or agents writing at once and needing isolation. Use a database with access controls.
  • Facts that change over time ("was true until March") or need contradiction handling (Chapter 14).
  • Memory that an index plus grep can no longer navigate reliably.
  • Semantic search over large collections. Letta's archival memory, described as “semantically searchable”, is an alternative.23
  • Task state that several agents claim and resume. Use a task graph such as Beads (in server mode; embedded mode has one writer, see Gotchas).

Use cases

1Solo developer, one repository

Situation
A developer retypes build/test commands and naming rules into each Claude Code session. The API rules matter only when the agent edits src/api.
Why it fits
CLAUDE.md loads at the start of every conversation, so facts arrive with no retrieval step.3 A rule in .claude/rules/ with a paths: field loads only when a matching file is read.3
Pair with
Git for history, an untracked CLAUDE.local.md for personal preferences,3 and /context all to see what loaded.

2Team that mixes coding tools

Situation
A small team shares one repository. Some use Claude Code and some Cursor, and conventions drift as each tool reads its own file.
Why it fits
AGENTS.md is an open format, and its site reports 60k+ open-source projects using it (vendor claim, not checked).4
Pair with
Share conventions in AGENTS.md; keep tool-specific files. Add @AGENTS.md to CLAUDE.md (Claude Code @path import syntax) to load the same file.3

3Your own agent with a notebook between sessions

Situation
You are building an agent on the Anthropic API and want findings to carry between runs, with no database.
Why it fits
The memory tool gives the model a /memories directory it checks before a task; your code picks the storage. The Python SDK ships BetaLocalFilesystemMemoryTool for a local folder (Part 2).1
Pair with
A request handler that rejects paths outside /memories.1

4Coding agent that resumes on another machine

Situation
A developer switches between laptop and desktop mid-feature; the next session needs completed, blocked and pending work.
Why it fits
Beads keeps the plan as a dependency graph and syncs it through the git remote.8 Tested in Part 3: after bd dolt push to a local bare remote, a clone running bd bootstrap reported only “Write login tests” in bd ready.
Pair with
CLAUDE.md for conventions, and one writer per database in embedded mode (see Gotchas).8

Scope and scale

QuestionAnswer
Cost per writeA hand edit needs no model call. In the API loop, the client runs the requested operations; continuing after their results takes another model turn.1 Storage is kilobytes.
Cost per readAlways-loaded files cost input tokens on every model turn. For ASCII English, assuming roughly four characters per token and decimal KB, 25KB is about 6,250 tokens; the line limit may bind first, so count your own index. An on-demand read adds a tool call and the file's tokens afterward.
What breaks firstFor Claude Code auto memory, the index load cap: about 200 one-line entries fit.3 Other tools hit their own context or navigation limits. With several writers there is no isolation or locking (see Gotchas).

  3. Check a code-linked note

    Add a source file and a note recording its file, symbol and commit.

    bashTested
    mkdir -p src/net && echo "export function send() {}" > src/net/send.ts
git add src && git commit -qm "feat: add send"

---
file: src/net/send.ts
symbol: send
commit: $(git rev-parse HEAD)
---
send() never retries
EOF

    Save this as check_notes.sh and run bash check_notes.sh from the repository root or a session-start hook. Use unquoted values between opening and closing --- lines at the top.

    bashcheck_notes.shTested
    set -euo pipefail
shopt -s nullglob globstar
for note in docs/memory/**/*.md; do
  fm=$(awk '{sub(/\r$/, "")}
            NR==1 && /^---$/ {p=1; next}
            p && /^---$/ {ok=1; exit}
            p {b=b $0 ORS}
            END {if (ok) printf "%s", b; else if (p) print "!malformed"}' "$note")
  if [ "$fm" = "!malformed" ]; then
    echo "STALE $note: unclosed frontmatter"
    continue
  fi
  n=$(printf '%s\n' "$fm" | grep -Ec '^(file|commit|symbol):' || true)
  [ "$n" -gt 0 ] || continue
  field() {
    printf '%s\n' "$fm" | sed -n "/^$1:/ {s/^$1:[[:space:]]*//;
      s/[[:space:]]*$//; p; q;}"
  }
  f=$(field file)
  c=$(field commit)
  if [ -z "$f" ] || [ -z "$c" ]; then
    echo "STALE $note: missing file or commit field"
  elif ! git rev-parse --verify --quiet "$c^{commit}" >/dev/null; then
    echo "STALE $note: commit unavailable"
  elif [ "$(git cat-file -t "$c:$f" 2>/dev/null)" != blob ]; then
    echo "STALE $note: path absent at recorded commit"
  elif [ ! -f "$f" ]; then
    echo "STALE $note: path missing from working tree"
  elif ! git diff --quiet "$c" -- "$f" ||
       ! git diff --cached --quiet "$c" -- "$f"; then
    echo "STALE $note: changed since recorded commit"
  fi
done

    The clean note prints nothing; changing src/net/send.ts adds a STALE line:

    textTested output

Gotchas

Gotcha: caps truncate and conflicts persist

Auto memory loads only the "first 200 lines or 25KB" of its index. If the index is over the limit, the write succeeds, but Claude Code returns an error telling Claude to rewrite it.3 Put detail in topic files. Contradictions persist too: "If two instructions contradict each other, Claude may pick one arbitrarily."3

Gotcha: two writers can lose data

Tested: this book reproduced a lost update when two writers read the same old file and replaced it without locking. A controlled schedule proves possibility, not frequency; the test is in the companion repository, benchmarks/stores. Inside the repository, use one writer per checkout, or one branch and worktree each, commit edits and review the merge; git cannot recover an uncommitted edit overwritten in a shared checkout. Auto memory is not protected this way: all worktrees share one folder outside the repository, so run one writing session per repository at a time or turn it off in parallel worktrees. Have every cooperating writer lock the same lock file before reading and hold it through replacement; that prevents lost updates. Write a temporary file beside the target and rename it over the target so readers see no partial file. Neither prevents contradictions.

Beads' default embedded mode (the database runs inside bd) has one writer; several agents need server mode (a separate Dolt server; documented, not tested).8 Divergent pushes were not tested: run bd dolt pull before each session, bd dolt push after it, and do not work on both machines between syncs.

Gotcha: cloned memory is untrusted input

Before the first run, review the instructions your harness can load from a cloned repository, including imports and path-scoped rules, as you would a build script (Chapter 17: memory poisoning).

  • Letta's default block limit: the documentation gives the unit (characters) and examples, not a default.7

Verdict

Verdict: start here

A few Markdown files, a short index and git give memory that people can read, review and move between tools, with no service to run.1,2 Keep CLAUDE.md to 200 lines or fewer and the auto memory index within its 200-line, 25KB cap. Add a task graph such as Beads to share a plan across sessions or machines (run bd reclaim to recover expired claims), and code-linked fields for notes about code that changes.

Move on when several users or writers need isolation (Chapter 08), facts need dates or contradiction handling (Chapter 14), you would rather have the model maintain cross-linked pages than curate by hand (Chapter 02), or an index plus grep misses paraphrased facts (Chapter 05, with embeddings from Chapter 03). Worked example: Chapter 21 keeps a painter's owner-edited procedures as Markdown files beside one SQLite file.
