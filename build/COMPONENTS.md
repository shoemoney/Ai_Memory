# Component reference for chapter authors

This is the contract for writing a chapter. Use only the components below. Do not add CSS, inline styles, scripts, images or fonts. If a layout need is not covered, write plain paragraphs, lists or tables instead and tell the person who owns the design system.

The finished sample chapter is `chapters/01-flat-files.html`. Copy its structure.

## 1. Files and building

| Item | Rule |
|---|---|
| Chapter file | `build/chapters/NN-slug.html`, for example `07-redis.html`. NN is two digits and matches `data-ch`. |
| Part divider | Generated in memory before the first chapter of each part. Legacy `NN-0-part-x.html` and `NN-0-appendix.html` files are ignored; authors do not maintain them. The appendices have no divider page: each starts with a one-line heading (`.appendix-head`). |
| Content of a file | A fragment. No `<html>`, `<head>`, `<body>`, `<script>` or `<link>`. |
| Order | Front matter, numbered chapters in numeric order (each part divider before its first chapter), Appendix A glossary, Appendix B (the attached-files index in the ebook, the code-files index in the print edition). A file containing `glossary` in its name is Appendix A regardless of its numeric prefix. |
| Build | `build/build.sh` writes `build/guide.html` and `build/ai-memory-guide.pdf` (the ebook edition). `EDITION=print build/build.sh` writes `build/guide-print.html` and `build/ai-memory-guide-print.pdf` (8.5 x 11 in paperback interior). `EDITION=hardcover build/build.sh` writes `build/guide-hardcover.html` and `build/ai-memory-guide-hardcover.pdf`, the hardcover interior at the supported 8.25 x 11 in trim: same content, margins and layout rules as print, with the trim and the full-bleed cover and part dividers set in `build/guide-hardcover.css`, which only this edition loads. Its page count differs from print, so a hardcover cover needs the hardcover count. Every build also writes `build/listings-manifest.json`. It exits non-zero on any error. |
| Cover image | `build/make-cover.py` composes `cover-art/cover-ai-memory.jpg` from the source PNG (full page width, extended with matching navy, JPEG). `build.sh` runs it first. `build.py` embeds the JPEG as a data URI. The cover is the only place an `<img>` is allowed (`00-front.html`, `src="cover-art/NAME.jpg"`). |
| Test the components | `build/check-components.sh` builds every snippet in this file and fails if any snippet breaks the rules. |

The build checks your file before it renders. It fails on: an em dash, a phrase like "generated by", a duplicate id, a citation with no matching source, a table with too many columns, a table without `<thead>`, a code line over 100 characters, a script or external resource. It warns on inline `style=` attributes and code lines over 88 characters. After rendering it fails if text runs outside the margins or a page is blank, and it fills in the contents page numbers from the real PDF.

The seven parts and their accent colors are fixed. Set `data-part` to the letter of your part.

| Letter | Part | Accent |
|---|---|---|
| a | Files and text | blue |
| b | Vectors and retrieval | teal |
| c | Models that remember | violet |
| d | Stores | red-orange |
| e | Frameworks and graphs | amber |
| f | History, research and practice | green |
| g | Case studies: local models only (chapters 20 to 23) | rose `#a13568` |

Appendices use the separate slate reference accent (`#3f4d66`). `make-dividers.py` generates divider markup in memory; the build ignores old divider fragments on disk and never rewrites chapter files.

## 2. Chapter skeleton

Every chapter has exactly this shape. The nine `<h2>` titles and their order are fixed, because the contents page and the reader's expectations depend on them. Use `<h3>` for subheadings inside a section.

```html-skeleton
<article class="chapter" data-ch="07" data-part="d" data-running="Redis">

  <header class="opener"> ... </header>                   <!-- component 3 -->

  <section><h2>What it is</h2> ... </section>
  <section><h2>How it works</h2> ... </section>
  <section><h2>Good for and not for</h2> ... </section>
  <section><h2>Use cases</h2> ... </section>
  <section><h2>Numbers</h2> ... </section>
  <section><h2>Setup walkthrough</h2> ... </section>
  <section><h2>Gotchas</h2> ... </section>
  <section><h2>Verdict</h2> ... </section>
  <section><h2>Sources</h2> ... </section>

</article>
```

| Attribute | Meaning |
|---|---|
| `data-ch` | Two-digit chapter number. Used for the page-header label and citation ids. |
| `data-part` | `a` to `g`. Sets the accent color. Chapters 20–23 are assigned to Part G at build time. |
| `data-running` | Short title for the running page header. Keep it under 40 characters. |

The chapter starts on a new page by itself. Do not add page breaks at the start.

## 3. Chapter opener

One per chapter. The `<h1>` is the only `<h1>` in the file. The big number is decoration and should repeat `data-ch`.

Maturity badge classes: `badge-shipped`, `badge-prototype`, `badge-research`, `badge-outdated`. Pick the one defined on the "How to read" page. Setup effort and running cost use the `rating` component with `r1` to `r5` and exactly five `<i></i>` children.

```html
<header class="opener">
  <p class="opener-eyebrow">Part D &middot; Chapter 07</p>
  <div class="opener-num" aria-hidden="true">07</div>
  <h1>Redis as agent memory</h1>
  <p class="opener-summary">One sentence in plain words that says what this approach is and does.</p>
  <div class="glance">
    <div class="glance-cell">
      <p class="glance-label">Maturity</p>
      <p class="glance-value"><span class="badge badge-shipped">Shipped</span></p>
    </div>
    <div class="glance-cell">
      <p class="glance-label">Setup effort</p>
      <p class="glance-value"><span class="rating r3" role="img" aria-label="3 of 5"><i></i><i></i><i></i><i></i><i></i></span><span class="of">3 of 5</span></p>
    </div>
    <div class="glance-cell">
      <p class="glance-label">Running cost</p>
      <p class="glance-value"><span class="rating r2" role="img" aria-label="2 of 5"><i></i><i></i><i></i><i></i><i></i></span><span class="of">2 of 5</span></p>
    </div>
    <div class="glance-cell">
      <p class="glance-label">Best for</p>
      <p class="glance-value">One line, under 110 characters, naming the user and the job.</p>
    </div>
  </div>
</header>
```

Rules: the title is at most 40 characters so it fits on two lines. The summary is one sentence, at most 140 characters. Ratings are your judgement from the numbers and steps in the chapter, so make sure the chapter supports them.

## 4. What it is, and terms

The `plain` box holds the explanation. The first paragraph uses `lead` and says what the thing is in plain words. Keep the box to three short paragraphs. Explain every term the first time it appears, either in the sentence or in the `terms` box. The `terms` box is optional and holds at most eight terms.

```html
<section>
<h2>What it is</h2>
<div class="plain">
  <p class="lead">A plain-language definition in two sentences.</p>
  <p>What it stores, where it runs, and who reads it.<sup class="cite"><a href="#s07-1">1</a></sup></p>
</div>
<aside class="terms">
  <p class="terms-title">Terms used in this chapter</p>
  <dl>
    <dt>Term</dt><dd>One-sentence meaning.</dd>
    <dt>Another term</dt><dd>One-sentence meaning with <code>inline code</code> if needed.</dd>
  </dl>
</aside>
</section>
```

## 5. How it works: diagram, figure and variants

Diagrams are hand-drawn inline SVG inside `<figure class="diagram">`. The CSS styles every shape, so use classes and never `fill`, `stroke` or `font-size` attributes.

Diagram rules:

- Always `viewBox="0 0 600 H"` with H at most 330. The SVG scales to the page width, so one unit is about 0.8 point. Never use another width.
- Text is 11px or larger (the classes do this). Put one short label per line. Break long labels into several `<text>` lines yourself, 30 characters at most per line inside a 170 wide box.
- Always set `text-anchor="middle"` and the center x for text inside a box.
- Add `role="img"` and an `aria-label` that describes the flow in a sentence.
- Arrows come from the build. Use `<path class="d-line" d="M x y H x2"/>` and the arrowhead is added at the end of the path.
- Leave at least 40 units of arrow length between boxes.
- Describe the diagram in the `<figcaption>`: "Figure N." in bold, then one or two sentences.

| Class | Use |
|---|---|
| `d-box` | White box with a dark outline. |
| `d-box soft` | Grey container or group. |
| `d-box accent` | Part-colored box for the main idea. |
| `d-box solid` | Filled accent box. Use `d-on-dark` on its text. |
| `d-box dark` | Near-black box, for the model or the final consumer. Use `d-on-dark` on its text. |
| `d-zone` | Dashed outline for a boundary such as a network or process. |
| `d-title` | Bold 12px label. |
| `d-sub` | Grey 11px detail line. |
| `d-mono` | 11px monospace, for file names and commands. |
| `d-label` | Small uppercase accent heading above a group. |
| `d-line` | Arrow. Add `accent` for the part color, `dash` for a dashed arrow, `plain-end` for no arrowhead. |

```html
<figure class="diagram">
<svg viewBox="0 0 600 150" role="img" aria-label="Diagram: an app writes to a store and the model reads from it.">
  <rect class="d-box" x="20" y="40" width="150" height="70" rx="4"/>
  <text class="d-title" x="95" y="70" text-anchor="middle">Agent app</text>
  <text class="d-sub" x="95" y="88" text-anchor="middle">writes and reads</text>

  <rect class="d-box accent" x="225" y="40" width="150" height="70" rx="4"/>
  <text class="d-title" x="300" y="70" text-anchor="middle">Store</text>
  <text class="d-mono" x="300" y="88" text-anchor="middle">memory:*</text>

  <rect class="d-box dark" x="430" y="40" width="150" height="70" rx="4"/>
  <text class="d-title d-on-dark" x="505" y="70" text-anchor="middle">Model</text>
  <text class="d-sub d-on-dark" x="505" y="88" text-anchor="middle">sees results</text>

  <path class="d-line" d="M170 75 H223"/>
  <path class="d-line accent dash" d="M375 75 H428"/>
</svg>
<figcaption><b>Figure 1.</b> The app saves facts to the store. A lookup returns the relevant ones to the model.</figcaption>
</figure>
```

After the figure, list the variants and tools in a data table (component 8), under an `<h3>`. Give the version or date for every named product.

## 6. Good for and not for

Two columns. Four to six bullets each. A bullet is one or two lines and names a concrete condition. Keep both columns about the same length.

```html
<div class="gnf">
  <div class="gnf-col good">
    <p class="gnf-title">Good for</p>
    <ul>
      <li>A concrete situation where this works well.</li>
      <li>Another situation, with a number if you have a sourced one.</li>
    </ul>
  </div>
  <div class="gnf-col not">
    <p class="gnf-title">Not for</p>
    <ul>
      <li>A concrete situation where it fails, and what to use instead.</li>
      <li>Another situation.</li>
    </ul>
  </div>
</div>
```

## 7. Use-case cards

Three to six per chapter. A card never splits across pages. Each card has a title and exactly three rows: Situation, Why it fits, Pair with. Keep each row to three lines or fewer. A situation must be specific: who, with what tool, and what goes wrong without it. A scenario you invented must read as an example. Open the section with the sentence shown below.

```html
<section>
<h2>Use cases</h2>
<p>Each scenario below is an example built from the documented behavior of the tools, not a report of a specific deployment.</p>
<div class="ucases">
<article class="ucase">
  <h3 class="ucase-title"><span class="n">1</span>Short name of the scenario</h3>
  <dl>
    <dt>Situation</dt><dd>Who is doing what, and the problem they hit.</dd>
    <dt>Why it fits</dt><dd>The property of this architecture that solves it.<sup class="cite"><a href="#s07-2">2</a></sup></dd>
    <dt>Pair with</dt><dd>What to combine it with, or when to move on.</dd>
  </dl>
</article>
</div>
</section>
```

## 8. Tables

Three table classes. Every table needs a `<thead>` so the header repeats on each page. Rows never split across pages. The body font is 9.3pt.

| Rule | Limit |
|---|---|
| Columns in `data` and `numbers` tables | 5 at most. Prefer 3 or 4. |
| Columns in a `matrix` | 7 at most (name plus 6 criteria). |
| Text per cell | Two or three short lines. Move longer text out of the table. |
| Width | Tables fill the text column. Set column shares with `<colgroup>` and the classes `c10` to `c70`. Shares must add up to 100. |
| Code in a cell | Use `<code>`. Long identifiers wrap on their own. |
| Links | Do not print URLs in cells. Cite with a superscript instead. |

`data` is the general table. The first column is bold. For a numeric column add `class="num"` to the `<th>` and every `<td>`.

```html
<p class="table-title">Variants and tools (state as of 20 November 2026)</p>
<table class="data">
  <colgroup><col class="c25"><col class="c45"><col class="c30"></colgroup>
  <thead><tr><th>Tool</th><th>What it is</th><th>Latest version</th></tr></thead>
  <tbody>
    <tr><td>Tool name</td><td>One-line description.<sup class="cite"><a href="#s07-3">3</a></sup></td><td>1.2.3, released 2026-10-01</td></tr>
    <tr><td>Other tool</td><td>One-line description.</td><td>Version unverified</td></tr>
  </tbody>
</table>
```

`numbers` is for the Numbers section. Three columns: the figure in monospace, what it measures, and the evidence grade. Every number carries a pill. Pills: `official` (maintainer documentation or repository), `secondary` (third-party write-up), `vendor` (a company's claim about a competing approach), `example` (a value shown as an example, not a default), `unverified` (could not confirm). A figure you could not confirm also goes in an Unverified callout or is left out.

```html
<table class="numbers">
  <thead><tr><th>Figure</th><th>What it measures</th><th class="src">Evidence</th></tr></thead>
  <tbody>
    <tr><td>200 lines</td><td>Recommended length of one file.<sup class="cite"><a href="#s07-1">1</a></sup></td><td class="src"><span class="pill official">Official docs</span></td></tr>
    <tr><td>15K tokens</td><td>A vendor's estimate of cost.<sup class="cite"><a href="#s07-4">4</a></sup></td><td class="src"><span class="pill vendor">Vendor claim</span> <span class="pill unverified">Unverified</span></td></tr>
  </tbody>
</table>
```

## 9. Setup walkthrough

An ordered list with class `steps`. Each step has a `step-title` paragraph (required, it carries the step number), an optional explanation and one or more code blocks.

Every code block carries a tag:

- `tested`: you ran the exact text on this machine. Say in the section intro what you ran, the date and the tool versions. Never tag a block tested if you did not run it.
- `docs`: copied or adapted from official documentation and not run.

Code block rules:

- At most 88 characters per line. The build fails at 100. Lines that are too long wrap, but wrapped code is hard to copy, so break long commands with a trailing backslash.
- At most 28 lines for a block that must stay whole. A block never splits unless you add `splittable`.
- A step never splits across pages unless you add `step-long` to its `<li>`. Use `step-long` only for a step that contains more than one tall block.
- Escape `<`, `>` and `&` as `&lt;`, `&gt;` and `&amp;` inside `<pre>`.
- Use `<span class="c">` for a comment. Do not add other markup inside `<pre>`.
- The language label is lowercase: `bash`, `sql`, `python`, `markdown`, `json`, `yaml`, `text`. `code-file` is optional and shows a path.

```html
<section>
<h2>Setup walkthrough</h2>
<p>This sets up X on Ubuntu. The commands in step 1 were run on 20 November 2026 with X 1.2.3. The other blocks come from the documentation and were not run.</p>
<ol class="steps">
  <li>
    <p class="step-title">Start the service</p>
    <p>One or two sentences that explain the step.<sup class="cite"><a href="#s07-1">1</a></sup></p>
    <div class="codeblock">
      <div class="code-head"><span class="code-lang">bash</span><span class="code-tag tested">Tested</span></div>
<pre>docker run -d --name memlab -p 127.0.0.1:6379:6379 redis:8
<span class="c"># prints the container id</span></pre>
    </div>
  </li>
  <li>
    <p class="step-title">Write the config</p>
    <div class="codeblock">
      <div class="code-head"><span class="code-lang">yaml</span><span class="code-file">config.yml</span><span class="code-tag docs">From docs, not run</span></div>
<pre>memory:
  ttl: 300</pre>
    </div>
    <p class="small muted">Optional note under a block, for output or a caveat.</p>
  </li>
</ol>
</section>
```

For a file tree, add `tree` to the code block (`class="codeblock tree"`) so the box-drawing lines connect. Show output from a tested run in a second block with language `text`.

## 10. Callouts

Four kinds. The label text is free, but start it with the kind and a short phrase, for example "Gotcha: caps cut the end off". Keep a callout to five lines. A callout never splits.

| Class | Use it for |
|---|---|
| `gotcha` | A failure mode, trap or limit that costs the reader time. |
| `tip` | A short helpful fact, such as a command or a distinction. |
| `unverified` | A claim a source could not confirm. State the claim, who made it, and why it is not confirmed. |
| `verdict` | The recommendation. One per chapter, inside the Verdict section. |

```html
<aside class="callout gotcha">
  <p class="callout-label">Gotcha: short name</p>
  <p>What goes wrong, why, and what to do about it.<sup class="cite"><a href="#s07-1">1</a></sup></p>
</aside>

<aside class="callout tip">
  <p class="callout-label">Tip</p>
  <p>A useful fact in one or two sentences.</p>
</aside>

<aside class="callout unverified">
  <p class="callout-label">Unverified: short name</p>
  <p>A vendor reports X.<sup class="cite"><a href="#s07-4">4</a></sup> We could not confirm it against the maintainer's documentation.</p>
</aside>

<section>
<h2>Verdict</h2>
<aside class="callout verdict">
  <p class="callout-label">Verdict: short phrase</p>
  <p><strong>Pick it when</strong> the condition holds. Say it directly.</p>
  <p>Say when to move to a different architecture and name it.</p>
</aside>
</section>
```

Anything the research marks UNVERIFIED must appear in an Unverified callout, with a grade pill in the Numbers table, or be left out. Never state it as fact in body text.

## 11. Citations and sources

Every factual claim carries a superscript number that links to the source list at the end of the same chapter. Put the citation after the punctuation of the clause it supports. For two sources, put both numbers in one `<sup>` separated by a comma.

Rules:

1. Number sources in the order they first appear in the chapter, starting at 1.
2. Source ids are `sNN-k`, where NN is the chapter number and k is the source number. The link is `href="#sNN-k"` and the list item has `id="sNN-k"`.
3. Every source in the list is cited at least once, and every citation has a source. The build checks this.
4. A source entry has a short title, a grade in parentheses, and the full URL. The title includes the publication date when the page has one.
5. Name the grade: `official`, `maintainer blog`, `secondary`, `vendor`, or a short note such as `quote read through secondary posts`.
6. Print full URLs in the list only. Do not put URLs in body text.
7. Quote exactly or paraphrase. Never put words in quotation marks that the source did not use.

```html
<p>Claude Code loads these files "at the start of every conversation".<sup class="cite"><a href="#s07-1">1</a></sup> A second claim has two sources.<sup class="cite"><a href="#s07-1">1</a>,<a href="#s07-2">2</a></sup></p>

<section>
<h2>Sources</h2>
<ol class="sources-list">
  <li id="s07-1"><span class="src-title">Claude Code memory documentation</span> <span class="src-note">(official)</span><a class="url" href="https://code.claude.com/docs/en/memory">https://code.claude.com/docs/en/memory</a></li>
  <li id="s07-2"><span class="src-title">Example blog post (2026-02-12)</span> <span class="src-note">(secondary)</span><a class="url" href="https://example.com/post">https://example.com/post</a></li>
  <li id="s07-3"><span class="src-title">Example reference</span> <span class="src-note">(official)</span><a class="url" href="https://example.com/ref">https://example.com/ref</a></li>
  <li id="s07-4"><span class="src-title">Example vendor page (2026-09-11)</span> <span class="src-note">(vendor)</span><a class="url" href="https://example.com/vendor-page-with-a-very-long-path/that-keeps-going/and-wraps-onto-a-second-line">https://example.com/vendor-page-with-a-very-long-path/that-keeps-going/and-wraps-onto-a-second-line</a></li>
</ol>
</section>
```

Long URLs wrap on their own. The example URLs above are for layout tests only. Use real sources in a chapter.

## 13. Decision flowchart

Also for the comparison chapter. Same SVG rules as diagrams. Shapes: `d-start` (pill, near-black), `d-decision` (diamond), `d-box accent` (answer), `d-end` (filled accent result). Label branches with `d-yes` and `d-no`. Keep it to five decisions at most per figure, and label every branch.

```html
<figure class="diagram">
<svg viewBox="0 0 600 245" role="img" aria-label="Flowchart: if more than one writer, use a database; else if you need search by meaning, use a vector store; else use flat files.">
```

## 15. Small helpers

| Class | Effect |
|---|---|

## 16. Page-break rules

- A chapter, a part divider, the cover and the contents each start a new page automatically.
- Never insert blank paragraphs, `<br>` or fixed heights to push content.
- Never wrap long runs of text in `avoid-break`. Only use it on blocks under a third of a page.
- A `figure.map-page` (section 21) always starts on a new page and the next block starts on a new page after it.
- Blocks that cannot split: figures, use-case cards, callouts, Good for and not for, code blocks, steps, terms box, source entries, table rows.
- Blocks that do split: paragraphs (three lines minimum on each side), lists, tables between rows, `splittable` code blocks and `step-long` steps.
- White space at the bottom of a page is normal when a block that cannot split moves to the next page. Do not fight it. Reorder only if a page is more than half empty.

## 17. Size budget

| Item | Limit |
|---|---|
| Chapter length | 8 to 12 pages including sources. |
| Body text | 10pt. Do not change it. |
| Table text | 9.3pt (9pt in a matrix, 8pt capital header labels, 8.8pt code in a cell). |
| Reference text | Glossary entries 9.5pt, sources 9.2pt with 8.2pt URLs, notes under blocks 9pt, figure captions 8.6pt. |
| Code text | 8pt, 88 characters per line. |
| Use-case cards | 3 to 6. |
| Source list | Up to about 25 entries. |
| Diagram height | 330 units at most, so a figure fits on one page with its caption. |

## 18. Things that break the layout

- A table with more than five columns, or long unbreakable words in a narrow cell. Shorten the text or use fewer columns.
- `<pre>` outside a `.codeblock`, or a code line over 100 characters.
- Inline `style` attributes, `<img>`, `<script>`, `<link>`, web fonts, `position: absolute`, or fixed widths.
- More than one `<h1>` in a chapter, or an `<h2>` that is not one of the nine template titles.
- A `figure.diagram` that does not use `viewBox="0 0 600 H"`, or text with a font size set by hand. (The full-page map in section 21 has its own viewBox rule.)
- Putting a citation in a heading. Cite in the text under it.
- Raw `&`, `<` or `>` in text or code. Escape them.
- Nested tables, nested callouts, or a callout inside a table cell.
- Empty `<p>` tags, repeated `<br>` tags, non-breaking spaces used for layout.
- Reusing an id, or citing a source number that is not in the list.

## 19. Writing rules

- Short, direct sentences. Say what a thing does, then its limit.
- Explain a term the first time it appears, in the sentence or in the terms box.
- No em dashes. Use a period, a comma or a colon.
- No marketing words such as "powerful", "seamless", "robust", "cutting-edge" or "revolutionary".
- No credit, author or byline, and no mention of the tool or model that wrote the text. Do not write "generated by", "written by" or similar.
- Every factual claim has a citation. Do not invent versions, commands, numbers or quotes. If the research file marks something UNVERIFIED, use an Unverified callout or leave it out.
- Dates are written as 20 November 2026, or 2026-11-20 inside a source title or table.
- Do not use first-person plural for results you did not produce. "We ran" is allowed only for code you actually ran.

## Automatic code listings, labels and the two editions

The build requires Python 3, PyMuPDF and Beautiful Soup 4 (`bs4`), plus Chrome. Chapter files are never
rewritten: everything below happens at build time.

**Labels.** Every `.codeblock` with a nonempty `.code-file` header gets a label `chNN-codeKK`: the chapter
number, then a two-digit counter in document order within that chapter, starting at 01. A file name that
appears twice in a chapter keeps its first label. The book cites the label. File and attachment names are
never renamed (walkthrough commands call files by their real names). A block that stays inline shows the
label in its header, left of the file name.

**Line limit.** `LISTING_LINE_THRESHOLD` in `listings.py` is **8**, one constant for the whole build
(`GUIDE_LISTING_LINES` overrides it for page-count experiments only). A named block of **more than 8 lines**
leaves the page and is replaced by a pointer; a named block of 8 lines or fewer stays inline with its label.
Unnamed blocks and output-only blocks always stay inline. Mark explicitly named output with
`class="codeblock output"` or `data-output`; a language label of `output` also marks output. A `text` label
alone does not mark output. An unnamed block over 40 lines produces a lint warning: give it a file name.

Authors may add a short description on the block; the build keeps it under the pointer and in the index:

```html
<div class="codeblock" data-listing-note="Builds both indexes from the same notes.">
  <div class="code-head"><span class="code-lang">python</span><span class="code-file">index.py</span><span class="code-tag tested">Tested</span></div>
  <pre>print("example")</pre>
</div>
```

**Pointer.** The pointer is a compact bar: language, label, line count and the evidence tag, then the note.
The code lives in the companion repository at `https://github.com/shoemoney/Ai_Memory/blob/main/<path>`, where
`<path>` is the attachment name (`ch13/letta-smoke.py`). Authors write the original code block and never maintain
a pointer.

| Edition | Pointer | Files | Sources lists | Index appendix |
|---|---|---|---|---|
| `ebook` (default) | Label and file name are one link to the repository URL (the URL is not printed), the line count, "attached to this PDF and in the companion repository", then the note. | Every named block and the three maps are attached to the PDF, named `chNN/<file>` (repeats within a chapter: `chNN/step-N/<file>`). | The title is the link; the URL stays as the `href` and is not printed. Three columns. | "Attached files": label, path, lines and note sorted by label, the repository URL and clone line, how to open attachments, a pymupdf snippet. |
| `print` | Label and line count, then the full URL as visible text (it may wrap), then the note. Nothing mentions attachments. | Nothing is embedded. | Title and the full URL in small type, two columns. | "Code files": label and path, with the repository URL and clone line at the top. |

Text that differs by edition is written once in the chapter source between `<!--ed:ebook-->...<!--/ed-->` and
`<!--ed:print-->...<!--/ed-->`; the build keeps the block for the edition being built. Use it only where the
sentence would be false in the other edition (for example "attached to the PDF").

**Manifest.** Every build writes `build/listings-manifest.json`: one object per named code file with `label`,
`chapter`, `path`, `lines`, `note`, `inline` (true when the block stayed on the page), and `url`. The companion
repository index is generated from it.

Source files are attached with their exact decoded code text, encoded as UTF-8. Readers can save them from their
PDF reader's attachments panel (ebook only). PDF outline titles come from normalised heading text.

## Citation and listing lint

A citation must link to an entry in **that chapter's** `.sources-list`. Its visible
number must match the entry's number in the ordered Sources list (including `start`
and `value` attributes). IDs may be numeric (`s05-18`) or descriptive. A missing
entry, missing link, wrong chapter or mismatched visible number fails the build
with the source file and line. Uncited Sources entries and citation numbers out of
order of first appearance produce warnings with file and line. Repeated citations
do not affect first-appearance ordering. A code block over 40 lines without a file
name produces a warning; add the name to give it a label, a manifest entry and an
attachment. PDF outline titles come from normalized heading text, preserving spaces
at wrapped lines and explicit `<br>` breaks.

For a comparison build only, `GUIDE_RELOCATE=0` disables relocation while retaining
attachments and back-matter ordering. Use separate `GUIDE_HTML` and `GUIDE_PDF` paths
when comparing builds. Shared chapter edits and shared generated outputs must never
be used as a scratch area for tests.
