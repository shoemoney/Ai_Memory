# Walkthrough outline: teaching a model a small command vocabulary

1. Open with the measured result, once available. Placeholder title: “[A tool accuracy] with [A prompt tokens] versus [B values].” Show one chart: tool accuracy with paired uncertainty versus actual prompt tokens. Link the raw results and frozen configuration. Until training runs, label all accuracy values pending; the first-turn token count is the only measured headline.
2. Explain the problem in plain language. A tool catalog repeats instructions on every turn. A fixed small set of commands may be learnable. A ten-line command guide is the practical middle step. Prompt length does not directly establish speed; measure that separately on the intended runtime.
3. Wrap each intent in a short bash function. Source one tools.sh file. Give each function one argument and put defaults inside. Show web_search, calc, and remember/recall. Demonstrate tools_help and command -h. Start with fake outputs so the reader needs no account or key.
4. Generate verified examples. User request, one native bash tool call, real subprocess stdout, short final answer. Include direct answers, dependent two-tool sequences, help requests, and unsupported flags. Explain why fake results depend on the input and why memory must be isolated per conversation.
5. Freeze the test before training. Show counts 4,000/400/400, split-disjoint wrappers and argument IDs, 30% no-tool requests, and the held-out search-then-read combination. Explain template limits and the CC0 generated-data dedication. Save hashes.
6. Render the conversations using Inkling's own renderer. Match effort 0.0 on both paths. Show the decoded native tool invocation from a round-trip test. Train loss on every assistant call and final answer; mask user/tool text. Count exact tokenizer inputs and reject overlong rows.
7. Inspect the dry run. One command prints data counts, exact tokens, 125 updates and the conservative budget. Explain training and evaluation charges separately. Placeholder for final service bill and retained-checkpoint cost.
8. Train the adapter later. Rank 32, one pass, shared AdamW loop and LR helper. Authenticate first, inspect W&B, save config, evaluate initial and periodic validation, and use fresh sampler clients after saving. Do not select on test.
9. Run A/B/C on the same held-out requests. A adapter without tool text, B stock with full schema text, C stock with ten lines. Execute only permitted functions, feed their actual output back, and retain complete traces. Show one success and one failure for every arm once available.
10. Measure outcomes, not only tool syntax. Full command-sequence accuracy, execution validity, no-tool precision/specificity, exact final answers, prompt/completion tokens by turn. TTFT remains unavailable if the API does not report it. Apply the registered 5-point margin, 20% prompt-token threshold, absolute accuracy and no-tool gates. Placeholders: table, paired interval, held-out combination result.
11. Close with the practical boundary. Fake fixtures prove the interface behavior only. Real retrieval, image quality, broader language and new tools need separate tests. Publish nulls, failures, exact prompts, hashes, traces and commands. Avoid claims about local speed until measured on that runtime.
